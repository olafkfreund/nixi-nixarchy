# Intent: Drop the `@ff-labs/fff-node` native index from `@` file search

## Problem

`bridge/files.js` imports `@ff-labs/fff-node` and builds an in-memory index of
`$HOME` to answer the launcher's `@` file search. It is the only native
dependency in the bridge, and it is expensive out of proportion to what it buys:

- It ships prebuilt `.so` files, so `nix/package.nix` needs `autoPatchelfHook`
  and `stdenv.cc.cc.lib` in `bridgeModules` (`nix/package.nix:41-45`) purely for
  this one package, plus an `installCheckPhase` assertion that the native
  library actually loads from the store (`nix/package.nix:255-258`).
- It needs a multi-minute scan before it answers anything. On the development
  machine `$HOME` holds 3,141,706 files; `initialize()` loops on
  `waitForScan(30_000)` and every request arriving before `ready` already goes
  to the fallback. The fallback is therefore not a theoretical safety net --
  it is what users get for the first minutes of every session.
- About 60 lines of `bridge/files.js` exist only to make its output usable:
  `usefulFuzzyMatch()`, `strictFileMatch()`'s fuzzy-suppression role, the
  `focused === true` branch, and the "FFF said complete but the file is not in
  the index" escape hatch at `files.js:296-301`.

Two complete fallbacks already exist and are already routed to: `fallbackFiles()`
does plocate, then `fd`, and `search()` calls it when the finder is missing, not
ready, errored, *or returned no rows*.

## Proposed outcome

- `@` file search is answered by plocate and `fd` alone.
- The bridge has no native dependency: `nix/package.nix` loses
  `autoPatchelfHook`, `stdenv.cc.cc.lib` and the `.so`-loads installCheck.
- `bridge/files.js` shrinks by roughly 60 lines and gains its first tests.
- Search stays usably fast and correctly ordered on a large `$HOME`.

## This is a feature trade, not dead-code removal

**Typo-tolerant fuzzy `@` search is lost.** This is the whole purpose of
`usefulFuzzyMatch()` and the `focused === true` path, and it is measurable.
Driving both code paths against the real 3.1M-file `$HOME` (`focused: true`,
settling on the last progressive emit):

| query           | FFF, index warm    | plocate/fd fallback |
| --------------- | ------------------ | ------------------- |
| `nixi`          | 281 ms, 100+ rows  | 457 ms, 100+ rows   |
| `.png`          | 278 ms, 100+ rows  | 338 ms, 100+ rows   |
| `hypr`          | 279 ms, 100+ rows  | 304 ms, 100+ rows   |
| `confguration`  | 241 ms, **48 rows**| 568 ms, **0 rows**  |
| `pakcage`       | 274 ms, **70 rows**| 546 ms, **0 rows**  |
| `files js`      | 223 ms, 25 rows    | 135 ms, 1 row       |

Read honestly:

- **The typo rows are the real loss.** `confguration` and `pakcage` return
  nothing at all from the fallback. Anyone who relies on approximate spelling
  in `@` search will notice immediately.
- **Speed is not a problem.** The fallback answers in 135-568 ms against a
  3.1M-file home -- same order as the warm index, and available instantly
  rather than after a multi-minute scan.
- **`files js` is not a regression.** Checked directly: `fd 'files.*js'` over
  `Downloads Documents Desktop` genuinely finds 1 file, at a 3 s, 15 s and 60 s
  timeout alike, so `fd` is not being truncated. FFF's other 24 rows were fuzzy
  matches such as `filesync.rs`, which contains no `js` at all. Different
  behaviour, not lost results.
- **Ordering is a real, separate regression.** FFF ranked user-facing paths
  first (`Videos/...`, `Pictures/screenshot-...png`, `Documents/...`). The
  fallback emits plocate's database order, which is path-alphabetical and so
  puts dotfile and cache noise at the top: `hypr` led with
  `.claude/jobs/0ffd7fbc/tmp/hyprcheck.log`, `.png` with
  `.agents/skills/herdr/assets/logo.png`. On a list capped at 100 rows that
  makes the result unusable for a common query. This one must be fixed as part
  of the change, not accepted.

Nothing found argues against proceeding, provided the ordering regression is
addressed. The user has decided to accept the loss of typo tolerance.

## Affected users and systems

- Everyone using `@` file search in the launcher and the card.
- `bridge/files.js`, `bridge/package.json`, `bridge/package-lock.json`,
  `nix/package.nix`.
- `spec/2026-09-15-8-overlay-on-omarchy-ask.md` and its plan describe the
  dependency as present. They are historical records of an approved decision
  and are not rewritten.

## Constraints

- `locatedUnderBase()` is a security boundary: it is what keeps a stale plocate
  database from surfacing paths outside `$HOME`. It must not be weakened, and
  it must be covered by a test.
- `bridge/files.js` has no tests today and is 38% of the untested bridge.
  Removing a code path from it without adding tests is not acceptable.
- `installCheckPhase` asserts specific bridge files exist. No assertion may be
  left pointing at something this change deletes.
- No new runtime dependency. `fd` and `plocate` are already required and already
  pinned in `nix/package.nix`.
