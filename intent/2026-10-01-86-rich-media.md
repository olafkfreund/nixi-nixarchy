# Intent: Nixi answers with rich media, and can show the user on their own desktop

## Problem

Nixi answers everything as a paragraph of prose, because that is all it is ever
given the chance to be.

The questions beginners actually ask do not all have prose answers. "What are
the window keys?" is a table — ten rows of key and action, which prose turns
into a wall the reader has to parse back into a table in their head. "What does
the Catppuccin theme look like?" is a picture. "How much has my store grown
since I started?" is three bars. "Where is that button?" is a screenshot with
the button in it — or, better, Nixi moving the pointer there while the user
watches.

The card is not the limitation. `Conversation.qml:1677` already draws every
reply with `textFormat: TextEdit.MarkdownText`. Rendered against a live
Quickshell 0.3.1 window configured exactly as the card configures it, these all
render today with no QML change at all:

- GFM tables, with borders and a header row
- task lists (`- [x]`), strikethrough, headings, fenced code blocks
- local images: `![](file:///path/x.png)`
- local **SVG**: `![](file:///path/chart.svg)`

`spacedMarkdown` (`Conversation.qml:154`), which every reply passes through,
leaves a table block intact — checked against a reply containing one.

What stops Nixi are four much smaller things:

1. **The bridge throws images away.** `messageText()` (`bridge/bridge.js:95`)
   returns `""` for every ACP content block that is not `type: "text"`. ACP
   defines `image` (base64 plus mimeType) and `resource_link` blocks; if an
   agent sends one today it is discarded before the UI can see it.

2. **The tutor brief never asks for rich answers.** `skills/nixi/SKILL.md` and
   `share/CLAUDE.md` instruct "2–6 sentences" and mention no table, image or
   chart. The agent follows the brief it is given, so it emits prose even where
   a table is plainly better.

3. **Charts collide with Guide.** For the agent to draw a chart it must write a
   file, which is a tool call, which Guide cancels by design
   (`bridge/trust-policy.js`). Left there, agent-drawn charts work only in
   Mechanic — which would make the safest trust level the least capable one,
   exactly backwards for a tool whose audience is beginners.

4. **Nixi cannot show anything on the desktop.** `newSession` passes
   `mcpServers: []` (`bridge/bridge.js:254`). ai-mirror is already installed and
   already speaks MCP over stdio (`ai-mirror mcp`), with its own consent dialog
   on the user's own desktop, a 30-second timeout and `SUPER+SHIFT+ESC` to
   revoke. Nothing in Nixi reaches it.

## Proposed outcome

A beginner asking a question that has a better-than-prose answer gets that
answer, in the card, without having to know it was possible.

Observable, in order of delivery:

1. **Tables.** "What are the window keys?" comes back as a rendered table.
   Nothing changes in the code — only the brief.
2. **Images.** An agent that sends an ACP image block, or names a local file,
   gets that image drawn inline in the reply.
3. **Charts, in Guide too.** A question with a numeric answer can come back as
   a small chart, and it still works at the default trust level, where the agent
   may not write to disk.
4. **The desktop, in Mechanic.** The user asks Nixi to show them rather than
   tell them; ai-mirror asks for control on their desktop; Nixi drives, and what
   it did comes back as a screenshot in the card.

Guide remains unable to change the machine. That is the line this work must not
cross.

## Affected users and systems

- **`bridge/bridge.js`** — the content-block path, and `newSession`'s
  `mcpServers`.
- **`skills/nixi/SKILL.md` and `share/CLAUDE.md`** — the tutor brief, which is
  where the behaviour actually changes for item 1.
- **`bridge/trust-policy.js`** — if ai-mirror is gated on trust, trust gains a
  new consequence.
- **`Conversation.qml`** — probably not, which is the point; the one real risk
  is message height (`Conversation.qml:1634` computes it from
  `agentText.contentHeight`).
- **A new media directory** under `$NIXI_DATA` holding images written out of
  ACP blocks and any generated charts. New state on disk that did not exist.
- **p620 and razer**, which run Nixi, and anyone running it from the flake.
- **ai-mirror**, which gains a second caller besides Claude Code.

## Constraints

- **Guide must not weaken.** The default trust level still cancels every
  permission request and cannot change the machine. Anything that makes rich
  media work in Guide must be Nixi's own code doing it, not the agent being
  granted something.
- **ai-mirror only in Mechanic.** Attaching a desktop-control MCP server while
  the card promises the agent cannot touch the machine would break the one
  guarantee the trust model makes.
- **MCP servers are not inside the ACP permission layer by default.** Issue #74
  established that a config-spawned `mcp_servers` entry is started at session
  start, outside the turn sandbox, with no permission request. Whether a server
  attached deliberately through `newSession`'s `mcpServers` produces ordinary
  per-tool permission requests must be *proved*, not assumed, before ai-mirror
  is attached — on each agent that Nixi supports.
- **No transcript persistence regression.** Nixi stores no transcript. Images
  written to disk must not become one by accident: they need a lifetime and a
  bound, not an ever-growing directory.
- **No new runtime dependency for charts.** No QtCharts, no charting library in
  the overlay, no WebEngine.
- **Untrusted content.** An image path or an ACP image block is data produced by
  a model. It must not be able to make the card read a file outside the media
  directory, and must not be rendered from a remote URL.
- **The 2–6 sentence discipline stays.** Rich media replaces prose where it is
  clearer; it does not license long answers with pictures attached.

## Open questions

1. **Who draws the chart?** Recommend the **bridge**, from a fenced
   ` ```nixi-chart ` block the agent emits: Nixi's own code writing an SVG needs
   no permission, so charts work in Guide, and no charting dependency enters the
   overlay. The alternative — the agent writing its own SVG with its file tools
   — is simpler to build and strictly worse, because it works only in Mechanic.

2. **One task or two?** Rich media (1–3) and desktop control (4) are separable;
   they are together here because ai-mirror's value in the card depends on the
   image path from item 2 (a screenshot is only useful if it can be shown).
   Recommend keeping them in one spec and splitting the plan into two halves
   that can ship independently, rather than two slugs.

3. **How long do generated images live?** Recommend a fixed-size directory
   pruned oldest-first on session start, so a long-lived card cannot fill the
   disk and nothing resembling a transcript accumulates.

4. **Does ai-mirror's own consent gate make Nixi's redundant?** ai-mirror
   already asks the human on their desktop and times out at 30s. Recommend
   Nixi's trust gate stays anyway — defence in depth, and the card's promise is
   Nixi's to keep, not ai-mirror's.

5. **Which agents must the ai-mirror permission behaviour be proved on before it
   ships?** Claude certainly. Codex and OpenCode are supported harnesses; given
   #74 and #75, recommend proving it on all three, and attaching ai-mirror only
   on the agents where it is proved.
