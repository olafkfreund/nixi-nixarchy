# Intent: The system board shows the user's other machines

Code: the companion (`nixoarchy-snowflake`: `app/server.py`, `app/plugins.py`,
the system board from #166), plus whatever runs on each host (the NixOS
config in `~/.config/nixos`, `hosts/{p510,p620,razer}`). Artifacts: this repo.
Depends on #166: its "gauges" look and readings are the starting point, and it
was approved as "this host only, in a shape that can take more".

## Problem

- **The board stops at this machine.** After #166, "system status" shows p620's
  (or razer's) own load, failed units and generation. The user runs several
  NixOS machines on one tailnet: p620 (workstation), p510 (server) and razer
  (laptop). To see how the others are doing they have to SSH in or open
  another tool.
- **The other hosts can't be asked today.** Nothing on p510 or razer answers
  a read-only status query: no host config enables a node exporter, and
  `:9100` gives no reply from either (checked 2026-11-04). Something has to
  run on each host, and that's a change to the NixOS config, not only to the
  companion.
- **The plugin sandbox can't reach them, and must not.** Stage plugins get
  their host readings from Nixi through a granted capability
  (`reads: ["system-status"]`), with no network for `nix-status`. A plugin
  that reached other machines would need network access and credentials,
  which #149 and #166 rule out.
- **Not every #166 reading means the same on another host.** Generation
  numbers are a counter per machine (p620's 420 and p510's 85 can be the same
  flake commit), so they can't say which host is behind. And p510 is a server
  with no desktop session, so it may have no user units to report.

## Proposed outcome

1. **"system status" shows this machine and the user's chosen peers.** Each
   host gets its own section of the #166 board, with the #166 readings it can
   honestly give, and a name the user recognises (p510, razer).
2. **Each host's status is honest about where it came from.** A peer that
   doesn't answer shows as unreachable, with when it last answered (or "not
   seen yet"), and never as idle or zero. A reading a host can't give (user
   units on p510) shows as unavailable. Each host shows what it's running in
   a form that can be compared across hosts (open question 7).
3. **The user picks the peers.** An explicit list, not discovery: nothing
   appears on the board that the user didn't add. Where the list lives is
   open question 3.
4. **Reading another machine needs its own yes.** A separate consent, "can
   read your other machines' status", shown once and switchable off. Without
   it, Nixi doesn't ask any peer, and the `system-status` grant from #166
   never carries peer readings. Switching it off stops collection at once and
   drops any peer readings Nixi holds.
5. **Peers answer read-only.** Whatever runs on a host reports status and
   accepts no commands: no restart, no rebuild, no "fix it" from the board.
6. **A peer that's off can't hold up the board.** This host's section shows
   at once; an unreachable peer costs at most a short, fixed wait, in the
   background, and is marked unreachable when it runs out.

## Affected users and systems

- **The user's hosts:** p620 and razer (they run the companion and show the
  board, and each is a peer of the other), and p510 (a server with no
  companion, which only answers).
- **The NixOS config (`~/.config/nixos`):** each answering host gains a small
  read-only service, or an exporter, reachable only over the tailnet.
- **The companion:** a collector in Nixi's server that asks peers for status
  outside the plugin sandbox, and settings for the consent (and the peer list,
  if it lives there).
- **The #166 board:** room for more than one host.
- **Others with the companion who have one machine:** nothing changes for
  them; with no peers there's no extra section, consent or traffic.

## Constraints

- **No plugin holds fleet credentials,** SSH keys or tokens, and no plugin
  gets network access to peers. If peer readings reach a plugin at all (open
  question 9), they come through a capability Nixi grants and the consent
  card names, and a plugin holding it never also gets network access.
- **Tailnet only.** A host's status service is reachable only on the tailnet
  interface (bound to it, or firewalled to it), never from the LAN or the
  internet.
- **Authorised on every request, both ways.** A host answers only an explicit
  list of the user's companion hosts, checked on each request, not "anything
  on the tailnet". Tailnet identity names a machine, not a process on it, so
  the spec says what stops another local program on p620 from asking too
  (open question 2). Nixi trusts an answer only from the host it asked.
- **Secrets follow the config repo's rules:** agenix, read at runtime from a
  file; never in the Nix store, a plugin folder or the companion's settings
  file.
- **Read-only by design,** not by convention: the host side offers no way to
  change the machine, and runs hardened and unprivileged, in its own module
  that's off until a host enables it.
- **Same privacy as #166, on every hop.** Peer readings go from the answering
  host to Nixi's server to the page only. Neither side logs them, and the
  answering host doesn't write a journal line per request. They're never put
  into the agent's prompt, and the spoken line about peers (open question 5)
  doesn't carry unit names into the conversation history.
- **#166's limits carry over to every host's section:** the 5-second refresh,
  at most 2 minutes, nothing asked while the board is closed, collapsed or
  the screen is locked; every value as text too, no state told by colour
  alone, Esc to close, reduced motion honoured; and the board still fits the
  stage frame's size limits with all hosts on it.
- **Cheap.** A short timeout per peer, no retries piling up, and nothing on
  an answering host runs heavier than what #166 runs locally.
- **Host config changes need the user's approval per host,** and a rebuild
  of each; p510 is a server and shouldn't need a restart of anything else.
- **The single-host board keeps working** with no peers configured, and
  doesn't change look.

## Open questions

1. **What answers on each host?** A Prometheus node exporter (standard, many
   readings, but no generation or failed-unit names without extra collectors,
   and a lot of data per request), a small read-only service that returns
   exactly the #166 readings (fits the board, but it's code to keep up), or
   Nixi's own server in a headless "answer only" mode (p510 has no companion
   today)?
2. **How is a caller trusted?** Tailnet identity alone (`tailscale whois`
   names the calling machine), that plus a shared token from agenix that only
   Nixi's service can read (so another program on the same machine can't
   ask), or mTLS?
3. **Where does the peer list live?** Nixi's settings (per machine, edited in
   the companion), or the NixOS config (declared once, so the peer list and
   each host's list of allowed callers stay in step)?
4. **One board or a switcher?** All hosts on one board (taller card), or this
   host first with a host switcher (tabs or "status of p510" by voice)?
5. **What does he say about peers?** Only problems ("p510 has one failed
   service, razer is off"), or a line per host?
6. **Which hosts answer?** p510 only, or every host, so p620 and razer can see
   each other (razer is often asleep, so it'd often be unreachable)?
7. **What counts as "behind"?** Show each host's flake revision and build
   date, flag a host whose revision differs from this one's, or both?
8. **Where does "last answered" come from** when a peer hasn't answered since
   Nixi started: remembered from earlier sessions, Tailscale's own "last
   seen", or "not seen yet"?
9. **Do peer readings go through the plugin?** Through `nix-status` with a
   second capability (the plugin draws every host and writes the spoken line,
   as in #166), or added to the board by Nixi itself (the plugin never sees
   other hosts, but then can't speak about them)?

## Reviews (Codex and agy, 2026-11-04)

The first draft (7440cba) was reviewed read-only by Codex (gpt-6-sol) and agy
(model not reported). Applied: consent enforced, not only shown (Codex);
caller allowlist checked per request, and a machine is not a process (both);
"older generation" needs a reference, and generation numbers don't compare
across hosts (both, questions 7); bounded wait instead of "costs nothing"
(Codex); "last seen" needs a source (both, question 8); headless p510 may
have no user units (agy); p620 is a peer of razer (agy); #166's limits and
the spoken line's privacy carried over (both); no per-request logging on the
answering host, hardening, agenix (agy); outcome 3 no longer pre-answers
question 3 (agy); question 9 added (agy).

Their recommended answers:

| # | Codex | agy |

| 3 | Nixi's settings, per machine | NixOS config, consent in Nixi |
| 4 | One board, this host first | One board, this host full, peers compact |
| 5 | Problems only | Problems only, or "all machines look fine" |
| 6 | razer answers when awake | Every host answers |
