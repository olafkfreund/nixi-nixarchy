# Intent: The system board shows the user's other machines

Code: the companion (`nixoarchy-snowflake`: `app/server.py`, `app/plugins.py`,
the system board from #166), plus whatever runs on each peer host (the NixOS
config in `~/.config/nixos`, `hosts/{p510,p620,razer}`). Artifacts: this repo.
Depends on #166: its "gauges" look and readings are the starting point, and it
was approved as "this host only, in a shape that can take more".

## Problem

- **The board stops at this machine.** After #166, "system status" shows p620's
  (or razer's) own load, failed units and generation. The user runs several
  NixOS machines on one tailnet: p620 (workstation), p510 (server) and razer
  (laptop). To see how the others are doing they have to SSH in or open
  another tool.
- **The other hosts can't be asked today.** Nothing on p510 or razer answers
  a read-only status query: no host config enables a node exporter, and
  `:9100` gives no reply from either (checked 2026-11-04). Something has to
  run on each peer, and that's a change to the NixOS config, not only to the
  companion.
- **The plugin sandbox can't reach them, and must not.** Stage plugins get
  their host readings from Nixi through a granted capability
  (`reads: ["system-status"]`), with no network for `nix-status`. A plugin
  that reached other machines would need network access and credentials,
  which #149 and #166 rule out.

## Proposed outcome

1. **"system status" shows this machine and the user's chosen peers.** Each
   host gets its own section of the #166 board, with the same readings, and
   a name the user recognises (p510, razer).
2. **Each host's status is honest about where it came from.** A peer that
   doesn't answer shows as unreachable, with when it was last seen, and never
   as idle or zero. A peer running an older generation says so.
3. **The user picks the peers.** A list in Nixi's settings, not discovery:
   nothing appears on the board that the user didn't add.
4. **Reading another machine needs its own yes.** A separate consent, "can
   read your other machines' status", shown once and switchable off, apart
   from the plugin's consent for this host.
5. **Peers answer read-only.** Whatever runs on a peer reports status and
   accepts no commands: no restart, no rebuild, no "fix it" from the board.
6. **A peer that's off costs nothing.** An unreachable host doesn't slow the
   board down or block this host's section from showing.

## Affected users and systems

- **The user's hosts:** p620 and razer (they run the companion and would show
  the board), and p510 (a server with no companion, which would only answer).
- **The NixOS config (`~/.config/nixos`):** each answering host gains a small
  read-only service, or an exporter, opened only on the tailnet interface.
- **The companion:** a collector in Nixi's server that asks peers for status
  outside the plugin sandbox, and a settings entry for the peer list and
  consent.
- **The #166 board:** room for more than one host.
- **Others with the companion who have one machine:** nothing changes for
  them; with no peers added there's no extra section, consent or traffic.

## Constraints

- **No plugin holds fleet credentials,** SSH keys or tokens, and no plugin
  gets network access to peers. Nixi collects peer status and gives it to the
  board the same way #166 gives this host's readings.
- **Tailnet only.** A peer's status endpoint listens on the tailnet interface
  (or is firewalled to it), never on the LAN or the internet.
- **Authenticated in both directions.** A peer answers only the user's own
  machines, and Nixi trusts an answer only from the host it asked. The spec
  says how (tailnet identity, a shared secret through the `nixos-secrets`
  path, or mTLS). No new secret goes into the Nix store or a plugin folder.
- **Read-only by design,** not by convention: the peer side offers no way to
  change the machine.
- **Same privacy as #166.** Peer readings go from Nixi's server to the page
  only; they're never logged or put into the agent's prompt. Unit names can
  be sensitive.
- **Cheap.** Peers are asked only while the board is open and visible, on
  #166's refresh, with a short timeout per peer and no retries piling up.
  Nothing on a peer runs heavier than what #166 runs locally.
- **Host config changes need the user's approval per host,** and a rebuild
  of each; p510 is a server and shouldn't need a restart of anything else.
- **The single-host board keeps working** with no peers configured, and
  doesn't change look.

## Open questions

1. **What answers on each peer?** A Prometheus node exporter (standard, many
   readings, but no generation or failed-unit names without extra collectors,
   and a lot of data per request), or a small read-only endpoint that
   returns exactly the #166 readings (fits the board, but it's code to keep
   up), or Nixi's own server in a headless "answer only" mode (p510 has no
   companion today)?
2. **How is a peer trusted?** Tailscale identity alone (simplest: only
   tailnet devices can connect, and `tailscale whois` names the caller), a
   shared secret per host via sops/agenix, or mTLS?
3. **Where does the peer list live?** Nixi's settings (per machine, edited in
   the companion), or the NixOS config (declared once, the same on every
   host)?
4. **One board or a switcher?** All hosts on one board (taller card), or this
   host first with a host switcher (tabs or "status of p510" by voice)?
5. **What does he say about peers?** Only problems ("p510 has one failed
   service, razer is off"), or a line per host?
6. **Does razer answer too,** or only show? It's a laptop that's often
   asleep, so it'd often be unreachable from p620.
