# Intent: A dark system board for "system status"

Code: the companion (`nixoarchy-snowflake`: `app/plugins.py`, `app/stages.py`,
`app/server.py`, `app/static/index.html`, the `nix-status` stage plugin).
Artifacts: this repo. Sibling: #167 (news), which needs the same kind of change.

## Problem

- **System status looks like a note, not a machine.** "nixi status" and
  "system status" run the `nix-status` stage plugin (#149 slice B). Its answer
  is three lines of text (generation, failed user services, store size) on the
  cream notebook, the same card a recipe or a definition gets. The user wants
  it to look and feel like a system monitor.
- **Plugins can only fill the notebook.** A stage plugin may return one kind,
  `facts` (`app/plugins.py:702`), and the page draws `facts` on the notebook.
  The other looks (board, map, cinema, sky, desk) are kinds reserved for Nixi
  and his agent. So no plugin can draw anything but a note, however good its
  data.
- **It says nothing about load.** No CPU, memory, disk or network figures, and
  nothing over time. A status check is a glance at a still list.
- **It closes before you've read it.** The notebook is read-only, so it closes
  itself after 20 seconds without a hover (`index.html:2366`).
- **He says nothing useful.** A plugin's answer is always spoken as "Here you
  go." (`app/server.py:4648`), whatever the status is.
- **It arrives like any other card.** Every notebook stage has the same
  entrance, so nothing signals "this is your system".
- **It only knows this computer.** The user runs several NixOS machines on a
  tailnet (p620, p510, razer, …). That part is a later task (see Constraints).

## Proposed outcome

1. **"system status" opens a dark terminal-style board, not the notebook.**
   It looks a bit like btop: monospace text, box-drawn panels, gauges and
   small graphs over time for the machine's load, failed services and the
   running generation. Its colours follow the omarchy theme. Which readings
   are on it is open question 2.
2. **It has its own entrance animation,** different from the notebook's, and
   a still version under reduced motion.
3. **The figures move while you're looking at it.** While the board is open
   and visible, the readings refresh and the graphs grow. When it closes,
   collapses to its tab, or the screen locks, nothing keeps sampling.
4. **It's supplied by a plugin,** as the user asked: the board shows a
   plugin's data, so the example can be replaced or switched off like any
   other plugin, and other plugins can use the same look.
5. **Every figure is honest.** A reading that couldn't be taken shows as
   unavailable, never as zero. Old readings say how old they are.
6. **This host only, in a shape that can take more.** v1 shows this machine.
   Nothing in it should need rework when other hosts are added by a later
   issue.

## Affected users and systems

- **Everyone with the companion and the `nix-status` plugin on,** on every
  host (p620 and razer today).
- **The plugin format (#149):** what a stage plugin may return grows beyond
  `facts`. Existing `facts` plugins keep working unchanged.
- **The stage frame (#144):** a new look beside board, map, cinema, sky, desk
  and notebook, and its own close and collapse behaviour.

## Constraints

- **The plugin sandbox and consent model stay as they are** (#149): no plugin
  markup, script or styles in Nixi's window; no new access without the consent
  card saying so; the hash check still switches a changed plugin off.
- **Host readings are given, not scraped.** What the board shows about the
  machine reaches the plugin through a capability Nixi grants and the consent
  card names (today `reads: ["system-status"]`), not by the plugin reading the
  host for itself. `nix-status` has no network, and keeps none.
- **Readings stay local.** They go from the server to the page only. They are
  never logged, and never put into the agent's prompt (as `day.py` does for the
  day desk). Unit and interface names can be sensitive.
- **Cheap while visible, free otherwise.** No sampling while the board is
  closed, collapsed or the screen is locked. A refresh must not make the
  desktop stutter on the slowest host (razer); the spec sets a budget.
- **Accessible.** Every gauge and graph shows its value as text too, so no
  state is told by colour alone. Contrast as in #155, keyboard close (Esc),
  reduced motion honoured.
- **It fits beside him** within the stage frame's size limits.
- **Other hosts are out of scope** here. If the user wants them, a later
  issue covers what runs on each host, which peers, how they're trusted, and
  a separate consent. No plugin ever holds SSH keys, tokens or fleet
  credentials.

## Decisions (approval, 2026-11-04)

The user approved this intent with the recommended answers:

1. **A general "gauges" look,** not a system-status-only board: it is the one
   that takes more hosts later without rework (outcome 6), and other plugins
   can use it.
2. **v1 readings:** CPU %, memory, disk (`/` and `/nix/store`), network in and
   out, failed user and system units, the generation, uptime. No temperature
   (sensors differ per machine).
3. **Refresh every 5 seconds while visible,** for at most 2 minutes; the board
   stays open while it updates, then collapses to its tab as other stages do.
4. **The plugin gives a short spoken line** in place of "Here you go."
5. **Other hosts are a later issue** (#168).

## Open questions (as drafted, answered above)

1. **A general look or a specific one?** A board made only for system status,
   or a general "gauges" look other plugins could use for other numbers (a
   UPS, a GPU, a build queue)? **The reviewers disagree:** Codex recommends the
   specific one (fewer choices about units and layout); agy recommends the
   general one (the validation is about the same size).
2. **Which readings are in v1?** For example CPU %, memory, disk (`/` and
   `/nix/store`), network in and out, temperature, failed *system* units as
   well as user units, the generation, uptime. More panels means a bigger
   card.
3. **How live, and how long does it stay up?** Codex suggests a refresh every
   10 seconds; agy every 4 seconds, stopping after 2 minutes. Should the board
   stay open past today's 20 to 30 seconds while it's updating?
4. **What does he say?** Keep "Here you go.", or let the plugin give a short
   spoken line ("all fine, one failed service")?
5. **Other hosts:** confirm they're a later issue, not part of this one.
