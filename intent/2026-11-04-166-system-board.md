# Intent: A dark system board for "system status", this machine and others

Code: the companion (`nixoarchy-snowflake`: `app/plugins.py`, `app/stages.py`,
`app/static/index.html`, a stage plugin). Artifacts: this repo. Sibling: #167
(news), which needs the same kind of change.

## Problem

- **System status looks like a note, not a machine.** "nixi status" and
  "system status" run the `nix-status` stage plugin (#149 slice B). Its answer
  is three lines of text (generation, failed user services, store size) on the
  cream notebook, the same card a recipe or a definition gets. The user wants
  it to look and feel like a system monitor.
- **Plugins can only fill the notebook.** A stage plugin may return one kind,
  `facts` (`app/plugins.py:702`), and the page draws `facts` on the notebook.
  The other looks (board, map, cinema, sky, desk) are built-in kinds the
  server fills itself. So no plugin can draw anything but a note, however
  good its data.
- **It says nothing about load.** No CPU, memory, disk or network figures, and
  nothing over time. A status check is a glance at a still list.
- **It only knows this computer.** The user runs several NixOS machines on a
  tailnet (p620, p510, razer, …) and has to ask each one separately, or open
  a terminal.
- **It arrives like any other card.** Every notebook stage has the same
  entrance, so nothing signals "this is your system".

## Proposed outcome

1. **"system status" opens a dark terminal-style board, not the notebook.**
   It looks a bit like btop: monospace text, box-drawn panels, gauges for CPU,
   memory and disk, small graphs over time, network in and out, failed
   services and the running generation. Its colours follow the omarchy theme.
2. **It has its own entrance animation,** different from the notebook's, and
   a still version under reduced motion.
3. **The figures move while it's open.** While the board is up, the readings
   refresh and the graphs grow; when it closes, nothing keeps sampling.
4. **It's a plugin.** The board is driven by a stage plugin's data, so the
   look can be used by other plugins and the example can be replaced or
   switched off like any other. Plugins still ship no HTML, CSS or script;
   the page draws the board from validated data.
5. **Other machines can appear on it,** when the user has said which ones.
   Each host has a row or a tab with the same readings, and a host that can't
   be reached says so instead of showing old numbers as current.
6. **Every figure is honest.** A reading that couldn't be taken shows as
   unavailable, never as zero. Old readings say how old they are.

## Affected users and systems

- **Everyone with the companion and the `nix-status` plugin on,** on every
  host.
- **The plugin format (#149):** a new data kind beside `facts`, with its own
  validation and limits. Existing `facts` plugins keep working unchanged.
- **The stage frame (#144):** a new set beside board, map, cinema, sky, desk
  and notebook.
- **For other hosts:** whatever runs on those machines to answer, and the
  tailnet between them.

## Constraints

- **The plugin sandbox and consent model stay as they are** (#149): no plugin
  markup, no new access without the consent card saying so, the hash check
  still switches a changed plugin off.
- **No secrets in a plugin.** A plugin never holds SSH keys, tokens or fleet
  credentials. Its sandbox can reach the network, so it must not become a way
  into other machines.
- **Readings of this host come from outside the sandbox.** Inside it, `/proc`
  describes the sandbox, not the machine, so a plugin can't sample load
  itself.
- **Cheap while open, free when closed.** No background sampling when the
  board is shut; a refresh must not make the desktop stutter on the slowest
  host (razer).
- **It fits beside him** within the stage frame's size limits, and the text
  stays readable (as in #155).
- **v1 is local unless the user decides otherwise** (open question 2).

## Open questions

1. **A general kind or a specific one?** One `sysboard` kind made for this, or
   a general "gauges" kind other plugins could use for other numbers (a UPS,
   a GPU, a build queue, a home lab)? **The reviewers disagree:** Codex
   recommends the specific `sysboard` (fewer choices about units and layout);
   agy recommends a general `gauges` kind (meters with a history, badges, up to
   six hosts), since the validation is about the same size.
2. **Other hosts in v1, or later?** Showing them needs something on each host
   to answer (node-exporter if one already runs, or a small read-only
   endpoint), a list of peers you choose, and a separate consent ("can read
   your other machines' status"). Both reviewers say the collecting is done by
   Nixi outside the sandbox, never by the plugin over SSH. Codex recommends
   local first, peers in a later slice.
3. **How live?** Codex suggests every 10 seconds while open; agy every 4
   seconds, stopping after 2 minutes. Faster looks more like btop but costs a
   sandbox start each time (each run hashes and copies the plugin folder).
4. **Which readings are in v1?** For example CPU %, memory, disk (`/` and
   `/nix/store`), network in and out, temperature, failed *system* units as
   well as user units, the generation, uptime. More panels means a bigger
   card.
5. **Does the plain-text "nixi status" answer stay?** The spoken answer could
   stay short ("all fine, one failed service") while the board shows the rest.
