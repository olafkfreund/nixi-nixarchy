# Intent: A question typed while the mic is open gets its board

## Problem

Clicking Nixi opens the mic ("listening…"). Pressing Return then opens the ask
box, but the mic stays open. If you type a question and send it, the board
never appears and you get a caption instead.

Seen live on p620 with "show me the latest world news": the caption read out
the stories and no slip appeared. With the mic stopped first (click twice,
"didn't catch that", then Return and type), the slip appeared 4 times out of 4,
including the fleet board.

Lines below are in `olafkfreund/nixoarchy-snowflake` at `0b5e20d`.

The cause is in `app/static/index.html`:

- `stageShow` declines while `rec` is set (line 2572). The answer falls back to
  a caption, whether the board comes with the answer (line 2827) or separately
  from a plugin (line 2198). A slip already on screen closes too.
- Starting the mic closes the ask box (`startRec`, line 2211), but opening the
  box doesn't stop the mic (`showAsk`, line 2668). The two don't match.

The open mic causes more than the missing board, because it keeps running
behind the typed question. All of this comes from reading the code, except the
one live run noted below:

- **Stray questions.** Whatever it hears is passed to `send` when the recording
  ends (line 2230).
  - While the typed answer is still running, an ordinary question gets "one
    sec" (line 2802). Commands and quick replies run before that check (lines
    2784-2801), so they can still act and speak mid-answer.
  - Once the answer has finished, it counts as a new question and cuts off his
    spoken answer (`shush`, line 2808). One live run transcribed "Being
    addressed" and replied to it. We don't know if that came from the speakers
    or from something else, such as keyboard noise.
- **A disturbed answer.**
  - Any noise loud enough to count as speech replaces your question in the
    caption with "…" (line 2221).
  - If it hears no speech, the server gives up after 8 seconds (`server.py`,
    line 2805). The page then clears your question and writes "didn't catch
    that" over the answer (line 2231).
  - If the input is completely silent, a mic error replaces the answer after
    about 1.5 seconds (`server.py`, lines 2806 and 2822; page, line 2229).

## Proposed outcome

- A typed question gets the same board with the mic opened first as without it,
  including the fleet board. That holds even if the board arrives while the mic
  is still shutting down, because `rec` stays set until the recording's stream
  ends (lines 2227 and 2234).
- Once you've chosen to type, nothing from that recording or from the follow-up
  window is sent as a question.
- A dropped recording leaves the typed question and answer alone: no
  "listening…", "…", "didn't catch that" or mic error over them, and no clearing
  of the caption.
- Voice works as it does today: click to talk, click to finish, push-to-talk,
  "hey Nixi", and answering an approval by voice. Saying "hey Nixi" is a clear
  request, so it still works while the ask box is open.

## Affected users and systems

- Fork `olafkfreund/nixoarchy-snowflake`: `app/static/index.html` for certain;
  `app/server.py` only if the decisions below need it.
- p620 and razer, which run the companion.
- Anyone who opens the mic and then types. Most printable keys open the ask box,
  unless a settings or other panel is open (line 3837), so this doesn't take
  Return specifically. The menu's `/cd` and Look items open it too (lines
  3015-3016).

## Constraints

- **Must:** a voice answer to an approval keeps working. That recording uses
  mode `approve`, and a stray key can open the ask box while it runs (line 3837).
  `endListening` already spares it (line 3019).
- **Must:** the other reasons to decline a board stay as they are: hidden, bar,
  calm, hover, fullscreen, locked and a pending approval (line 2572).
- **Must:** a fallback caption still appears wherever a board is declined, so no
  answer is lost.
- **Must not:** reopen the mic by itself when the ask box closes.
- **Must not:** keep any audio from a recording that was dropped.
- **Not in this issue:** the mic picking up speech from the speakers in general.
  The follow-up window ignores Nixi's own voice (`Wake.speaking`, `server.py`,
  line 2954), but a normal recording has no such check. If stray questions
  continue after this fix, that needs its own issue.

## Open questions

1. **What happens to the recording when the ask box opens?**
   Recommended: drop it at once, as `endListening` does. It's the mirror of the
   mic closing the box, and the mic is off while you type. The cost is that a
   stray key while you're talking throws that speech away.
   The alternatives are to keep listening until you send, or to finish the
   recording and send what was heard. Keeping it open leaves the mic running
   while you type, so the caption can still be disturbed and speech can still be
   sent. Finishing it sends half a sentence alongside your typed question.
2. **What if your speech is already being transcribed when the box opens?**
   Stopping the mic has no effect by then, and the text is sent whatever
   `cancelled` says (`server.py`, lines 2839-2840; page, line 2230).
   Recommended: discard the text, because you've moved on to typing. The
   alternative is to send it and leave the box open, which keeps a finished
   question but sends two questions if you carry on typing.
   Esc and hiding Nixi have the same gap today (lines 3821 and 3019). Discarding
   in the shared code would change those too, so that they also really cancel.
3. **Should a board that arrives while you're really listening wait, or fall
   back to a caption?** Boards can arrive unasked in the middle of a recording,
   for example from a slow plugin or video search (`server.py`, lines 4876
   and 4893).
   Recommended: leave this as it is (caption), because no one has reported it and
   a slip shouldn't open over someone talking. The alternative is to hold the
   board and show it when the mic closes, if it's still the current one. That is
   nicer, but it's new behaviour that a typed question doesn't need.
4. **Do other questions sent by hand get the same treatment?** Run on a slip
   (line 2603), Again in history (line 2952) and Quick actions (line 2963) can
   also send while the mic is open, and lose their board the same way (not tested
   live). "Continue this chat" sends nothing, but its restored caption can be
   wiped the same way (line 2954).
   Recommended: yes. End the recording when any question is sent by hand or a
   chat is resumed, not only when the box opens.
5. **Should typing also keep the follow-up window shut?** That is the short "just
   talk" window after he answers. It doesn't block boards, but speech heard
   during it is sent while you're typing (line 2160).
   Closing it once isn't enough: if he's still talking when the box opens, the
   window opens again when he stops (`Wake.talking_until`, `server.py`, line
   2964, called from `/api/speaking`).
   Recommended: yes, for as long as the box is open. The cost is that talking
   instead of typing then needs "hey Nixi" or a click.

## Reviews of the first draft (2026-11-04)

Every finding was checked against the code at `0b5e20d`. None was run live.

  - confirmed: a dropped recording can still disturb the caption;
  - confirmed: "nothing the mic hears" conflicted with keeping "hey Nixi", which
    can send while the box is open (line 2162);
  - confirmed: the 8-second limit and "any printable key" needed qualifying.
  All addressed above.
- **agy** (model not reported):
  - confirmed: the same `rec` and caption findings, plus the silent-mic error
    that comes before the cancel check (`server.py`, lines 2822 and 2834);
  - confirmed: while the answer is running, ordinary speech gets "one sec", but
    commands and quick replies still run;
  - confirmed: a new follow-up window can open while typing, which changed
    question 5;
  - confirmed: the second fallback path, the slip closing, and the earlier caption
    changes;
  - confirmed: Quick actions and "continue this chat" belong in question 4;
  - confirmed: Esc and hiding share the transcribing gap in question 2;
  - confirmed, no change needed: a normal recording left open makes an approval's
    voice answer give up at once (line 2209). This goes away if the recording is
    dropped when the box opens.
  - unverified: its estimate of 50-100 ms for the mic to shut down. The outcome
    above doesn't depend on the timing.
  - unverified: whether cancelling the follow-up window drops speech that is
    already being transcribed. The spec should check this.
  - not adopted: that cancelling must clear `rec` immediately. That's a design
    choice for the spec, so the outcome only states the result.
