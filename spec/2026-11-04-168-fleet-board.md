# Spec: The system board shows the user's other machines

Code: `olafkfreund/nixoarchy-snowflake` (the companion; references are to
`main` at 2e28c93, PR #32, plus the approved #166 spec, which this builds on),
this repo's Home Manager module (`nix/hm-module.nix`), and the user's NixOS
config (`~/.config/nixos`). #166 must be merged first: its `gauges` kind
already takes up to six hosts and `state: up | down | stale`
(#166 spec part 2), so the plugin format doesn't change.

Facts checked on 2026-11-04 that the design rests on:
- `getent hosts p510` gives `192.168.1.65` (the LAN), while `razer` gives
  `razer.tail833f7.ts.net` (the tailnet). A short host name is not a safe way
  to reach a peer.
- `nixos-version --json` has no `configurationRevision`: no host records the
  flake revision it was built from.
- No host sets `networking.firewall.trustedInterfaces`; nothing listens on
  port 9188.
- The config repo uses agenix (55 files; sops in 1).

## Design

### 1. `nixi-status`: the answering service (snowflake, `app/status_serve.py`)

- **One small stdlib-Python HTTP server,** shipped in the snowflake package as
  `bin/nixi-status`, reusing `system_status()` from `app/plugins.py` (as
  extended by #166 part 3). One endpoint, `GET /v1/status`; every other
  method or path gets 404. It has no endpoint that changes anything (intent
  outcome 5).
- **What it returns** (JSON, at most 16 KiB):

  | Key | Source |
  |---|---|
  | `host` | `socket.gethostname()` |
  | `cpu_pct`, `mem`, `disks`, `net`, `uptime_s`, `failed_system` | `system_status()` (#166 part 3) |
  | `failed` | always `null`: a system service has no user session to ask (intent: "user units on p510 show as unavailable") |
  | `generation` | as #166 |
  | `rev` | `configurationRevision` from `nixos-version --json`, `null` if unset (part 5 sets it) |
  | `built` | the mtime of `/run/current-system`'s target, as ISO 8601 |

  Rates (CPU, network) come from the previous reading the server keeps in
  memory; the first request after start falls back to #166's 250 ms double
  read.
- **Who may ask, checked on every request, in this order:**
  1. The source address is in the tailnet ranges (`100.64.0.0/10`,
     `fd7a:115c:a1e0::/48`); otherwise the connection is closed with no
     answer.
  2. The source address is one of the addresses of the allowed callers
     (`allowedCallers`, part 4), resolved by their full MagicDNS names and
     cached for 60 s. A name that resolves outside the tailnet ranges is
     dropped from the list.
  3. `Authorization: Bearer <token>` matches the fleet token
     (`hmac.compare_digest`). The token is what stops another program on p620
     from asking: tailnet identity names the machine, not the program
     (intent constraint).
  Any failure → 403, the same body each time, nothing logged per request.
- **No journal line per request.** `log_message` is silenced; only startup
  and a crash are logged, never a reading or a caller.
- **Bounded:** one request at a time per caller address (`Busy` → 429), a
  2 s read timeout, `system_status()`'s 1.3 s bound (#166).

### 2. The NixOS module (snowflake flake, `nixosModules.status`)

```nix
services.nixi-status = {
  enable = false;                 # off until a host turns it on
  port = 9188;
  allowedCallers = [ ];           # full MagicDNS names, e.g. "p620.tail833f7.ts.net"
  tokenFile = null;               # agenix path; required when enabled (assertion)
};
```

- **systemd service `nixi-status`:** `DynamicUser=true`,
  `LoadCredential=token:${tokenFile}` (so the token is read from
  `$CREDENTIALS_DIRECTORY`, never the store), `ProtectSystem=strict`,
  `ProtectHome=true`, `PrivateTmp=true`, `NoNewPrivileges=true`,
  `CapabilityBoundingSet=` (none), `RestrictAddressFamilies=AF_INET AF_INET6
  AF_UNIX` (AF_UNIX for the system bus that `systemctl --failed` uses),
  `MemoryMax=64M`, `Restart=on-failure`. It starts after
  `tailscaled.service`.
- **Tailnet only, twice over:** the port goes only into
  `networking.firewall.interfaces.tailscale0.allowedTCPPorts`, never the
  global list, and part 1's address check refuses anything else even if a
  firewall rule were wrong.
- **Assertions:** `tokenFile` set; `allowedCallers` non-empty; every entry
  ends in `.ts.net`.

### 3. The collector in Nixi (snowflake, `app/peers.py`)

- **`collect(peers, token, deadline)`** asks every peer at once (one thread
  each) with a plain-HTTP `GET` over the tailnet (WireGuard already
  encrypts and authenticates the hosts) to
  `http://<magicdns-name>:<port>/v1/status`, 1.5 s timeout each, the whole
  call bounded by the same 1.5 s.
- **Nixi trusts an answer only from the host it asked:** it resolves the name
  itself, refuses an address outside the tailnet ranges (so `p510` →
  `192.168.1.65` can never be used), and connects to that address. WireGuard
  guarantees that address is that node.
- **Each result is checked like any untrusted input:** at most 16 KiB, JSON,
  each key against the types in part 1's table; anything wrong → that peer is
  `down` with "gave an answer Nixi can't read".
- **Per peer:** `{name, state: "up" | "down", status | null, last_ok}`, where
  `last_ok` is the time of the last good answer **in this session**, kept in
  memory only, or `null` ("not seen yet", decision 8). Nothing is written to
  disk.
- **Run alongside `system_status()`,** not after it, so a refresh is bounded
  by the slower of the two (about 1.5 s), inside #166's 3 s plugin limit.

### 4. Where the peer list and token come from

- **Declared once in the NixOS config** (decision 3), in
  `~/.config/nixos/hosts/common/nixos/`: one list `nixiFleet` of
  `{ name, fqdn, companion }` for p620, p510 and razer.
  - every host imports `nixosModules.status` with `enable = true` and
    `allowedCallers` = the `fqdn`s of the hosts with `companion = true` (p620,
    razer), so each host's callers and the peer list can't drift apart;
  - the companion hosts set the new Home Manager option
    `services.nixi.companion.peers` (this repo, `nix/hm-module.nix`) to every
    other host's `{ name, fqdn }`, and `services.nixi.companion.peerTokenFile`.
- **The HM module** writes the peer list (names and FQDNs, no secrets) to
  `~/.config/nixi-companion/peers.json` and passes the token path in the
  service environment as `NIXI_PEER_TOKEN_FILE`. With `peers = [ ]` (the
  default) neither exists and nothing in this spec runs.
- **The token** is one agenix secret, `nixi-status-token` (32 random bytes,
  base64), readable by root (for `LoadCredential`) on every host, and on p620
  and razer also by `olafkfreund` (mode 0400) for the companion. One fleet
  token, not one per pair: every caller is the same user's companion, and a
  per-pair token adds secrets without stopping anything the tailnet and the
  allowlist don't already stop.

### 5. Comparable revisions (decision 7)

- The user's flake sets `system.configurationRevision = self.rev or
  self.dirtyRev or null;` once for all hosts, so `nixos-version --json` reports
  the commit each host was built from (dirty builds show `…-dirty`).
- A host shows a `rev` badge (first 7 characters) and a `built` badge (date).
  A peer whose `rev` differs from this host's gets tone `warn` on that badge
  and the text "differs". When either side's `rev` is `null`, no comparison is
  made and the badge shows "—" (honest: unknown, not "same").

### 6. The capability and the consent

- **A second read, `peer-status`** (`app/plugins.py:156` accepts
  `("system-status", "peer-status")`). `_check` refuses `peer-status` with
  `network: true` exactly as #166 does for `system-status` ("a plugin that
  reads your other machines' status can't use the network").
- **Feed:** `run_stage` adds `feed["peers"]` (the list from part 3) only when
  all three hold: the plugin declares `reads: ["peer-status"]`, the user
  consented to that plugin (as #149), and the **"Other machines" switch** is
  on.
- **The "Other machines" switch** (decision: the consent stays in Nixi's
  settings): a new row in Settings → Plugins, off by default, shown only when
  `peers.json` lists at least one peer, reading "Let plugins show your other
  machines' status (load, memory, disks, failed services)". The first time a
  plugin with `peer-status` runs while it is off, the plugin's consent card
  shows the same sentence with an "Allow" button that turns it on (asked
  once, intent outcome 4).
- **Off means off:** while the switch is off `collect()` is never called and
  no peer is contacted. Turning it off clears the collector's in-memory
  results and `last_ok` times, and drops the plugin's cached stage
  (`plugins._cache`), so a cached board with peer sections can't come back.
- **Never in a prompt:** `feed["peers"]` reaches only the sandboxed plugin.
  The agent path (`plugin_stage_thread`, `server.py:4651`) returns to the
  agent only whether the stage showed, never its content (verified in the
  plan; if it returns more today, that is changed for `gauges`).

### 7. `nix-status` shows the fleet (`plugins/examples/nix-status/`)

- `plugin.json`: `reads: ["system-status", "peer-status"]`. Without the
  switch it gets no `peers` and draws one host, exactly as #166.
- **Hosts, in order:** this host (as #166), then each peer in the configured
  order, at most six in all:
  - `up`: CPU, MEM, `/`, STORE meters (no network meters for peers, to keep
    them compact), `rev` / `built` / `up` badges, and a "Failed (system)"
    list; user units show as the badge `user —` (unavailable, never "none").
  - `down`: `state: "down"`, no meters, one badge `last` = "not seen yet" or
    "14:02" (`last_ok`).
- **`say`, problems only** (decision 5): this host's #166 line, then one short
  clause per peer with a problem, without unit names: "p510 has one failed
  service.", "razer is off.", "p510 is on a different revision.". When nothing
  is wrong anywhere: "All machines look fine.". Capped at 200 characters
  (#166 part 1); past that, "and N more.".
- The folder changes, so the #149 "Changed" / "Updated" note shows once, as in
  #166 part 7.

### 8. The board with several hosts (`index.html`, the `term` set)

- **One board** (decision 4): the first host full, as #166; every further host
  as a **compact panel**: name in the border, its badges, its meters as one
  row each without sparklines, its failed count. Clicking or Enter on a
  compact panel expands it (and collapses the others); sparkline history is
  kept per host from the start, so an expanded peer shows its history.
- **A `down` host** is one line: "┤ razer ├ unreachable · not seen yet", in the
  dim foreground, never empty meters or zeros.
- **Size:** within #166's 340 px width; the board scrolls inside past its
  maximum height. With three hosts (one full, two compact) it fits without
  scrolling at 1080 p.
- **Accessible:** compact panels are buttons with `aria-expanded`; each row
  keeps its text value; `stageText()` reads every host, peers after this one.
  #166's reduced motion, contrast and Esc rules apply unchanged.

## Alternatives rejected

- **Prometheus node exporter:** no generation, revision or failed-unit names
  without extra collectors, and far more data per request than the board
  uses (decision 1).
- **Nixi's companion headless on p510:** a desktop app with a browser page,
  voice and an agent bridge, run on a server to answer one GET.
- **SSH to each peer:** a key the companion would hold, and a shell where a
  read-only answer is wanted; the intent forbids both.
- **`tailscale serve` with identity headers:** names the tailnet user, not the
  calling machine, and its config is set imperatively per host, outside the
  NixOS config.
- **`tailscale whois` for the caller check:** needs the tailscaled LocalAPI
  socket inside a `DynamicUser` service; resolving the allowed callers'
  MagicDNS names gives the same answer (a tailnet address belongs to exactly
  one node) with no extra access.
- **Short host names:** `p510` resolves to the LAN. Full MagicDNS names, and
  refusing non-tailnet addresses, rule that out.
- **A token per pair of hosts, or mTLS:** more secrets and rotation for the
  same set of callers; the tailnet, the allowlist and one token already make
  each request come from one of the user's companions.
- **Nixi asks peers on a timer and keeps "last seen" on disk:** traffic while
  nobody looks, and state the intent said not to keep (decision 8).
- **Peer readings added to the board by Nixi, past the plugin:** the plugin
  then couldn't write the spoken line (decision 9).
- **HTTPS on the tailnet:** WireGuard already encrypts and authenticates
  between nodes; certificates would add a renewal to every host for no new
  protection.

## Risks

- **MagicDNS fails** (p620's tailscale reports it can't reach its DNS servers
  today): peers can't be resolved, so they show `down`, and the caller
  allowlist empties on the answering side (every request refused). Fails
  closed, never open. The plan checks `getent hosts p510.tail833f7.ts.net` on
  each host first.
- **A tailnet address changes** (a node re-added): the 60 s cache means up to
  a minute of 403s for that caller.
- **`system.configurationRevision` changes every host's system closure** on
  the next rebuild (a new revision string per commit). Expected; one rebuild
  per host, which the intent already requires.
- **p510 is a server:** the new service is a new unit; enabling it restarts
  nothing else. Measured: memory under 64 MiB.
- **Refresh budget:** peers add up to 1.5 s in parallel with `system_status()`;
  a refresh stays inside #166's 3 s plugin limit, and a slow one is skipped
  (`Busy`), not queued.
- **Token leak** (e.g. read from p620 by another program running as the user):
  it lets that program read status from the fleet, nothing more. Rotation is
  one agenix rekey and a deploy.

## Verification

- **Unit (snowflake, `python3 -m unittest discover -s tests`):**
  - `status_serve`: a request from outside the tailnet ranges gets no answer;
    from a tailnet address not in the allowlist → 403; wrong token → 403; the
    right one → 200 with part 1's keys; `POST` and other paths → 404; no log
    line per request (captured log is empty); a name resolving to
    `192.168.1.65` is dropped from the allowlist.
  - `peers.collect`: three fake peers (one up, one timing out, one sending
    65 KiB) return within 1.6 s as up / down / down; a LAN address is refused
    without connecting; `last_ok` stays `null` until a good answer.
  - `_check`: `peer-status` with `network: true` refused.
  - `run_stage`: no `feed["peers"]` when the switch is off, or the plugin isn't
    consented, or doesn't declare `peer-status`; turning the switch off clears
    the collector and the plugin's cache.
  - `nix-status` in the real sandbox: one host without peers (as #166); with
    two peers (one down) valid `gauges` with three hosts, `say` with no unit
    names for peers, "All machines look fine." when all are fine.
- **Nix:** `nix flake check` in the snowflake (module evaluates; assertions
  fire on a missing `tokenFile`, an empty or short-named `allowedCallers`);
  `nix build` of p620, p510 and razer in `~/.config/nixos`.
- **Page (headless Chromium):** three hosts render one full and two compact;
  a `down` host shows "unreachable · not seen yet"; Enter expands a compact
  panel; `stageText()` reads all three.
- **Live:**
  - from p620: `curl` with the token to `p510.tail833f7.ts.net:9188/v1/status`
    → 200; without it → 403; from the LAN address `192.168.1.65:9188` → no
    connection;
  - `journalctl -u nixi-status` on p510 after 24 refreshes shows no request
    lines;
  - "system status" on p620 with the switch off shows only p620; after
    "Allow", p620, p510 and razer, with razer "unreachable · not seen yet"
    while it sleeps; his line is "razer is off."; switching it off and asking
    again shows one host;
  - the same from razer, with p620 as a peer.
