# Spec: chat replies

The approved intent allows chat replies "only for apps with a safe way to send" (open question 6, slice 6). This spec
first checks which apps on this desktop have one. Companion code is cited at `olafkfreund/nixoarchy-snowflake`
`origin/main` `8f2275e`. The shell is Omarchy's `omarchy-edge-20261104-cc99764`, at
`share/omarchy/shell/plugins/notifications/Service.qml`. Bridge code is in this repo at `509abe7`. Everything below was
checked read-only on p620 on 2026-11-07.

## What a safe send path needs

A reply is safe only if all four of these hold:

1. **A real API or CLI sends it,** not typed keys or a scripted browser.
2. **The destination comes from the service,** as an account, a conversation ID and a thread ID. It never comes from
   notification text, which any local program can fake (#215 spec, "A spoofed sender").
3. **The exact words are bound to that destination** when the card is shown. A newer notification can't change either.
4. **Only a click sends it** (#95). A spoken yes never sends.

## Findings

### The notification bridge can't carry a reply

- The shell never asks apps for inline replies. Its `NotificationServer` sets images, actions, markup, links and
  persistence, but not `inlineReplySupported` (`Service.qml:1459-1466`). Quickshell 0.3.2 has the property and it
  defaults to off, so the shell doesn't offer inline replies. Even if an app sent one, the row below couldn't carry it.
- A handed-over row has only `key, app, source, summary, body, urgency, category` (`Service.qml:705-706`). It has no
  conversation, thread or account. `body` is cut to 200 characters there, and Nixi cuts it again to 120 and blanks it
  unless `notify_details` is on (`server.py:2239-2262`).
- `/api/notify/act` accepts only `open` and `dismiss` (`server.py:6206-6217`).

So no reply can be bound to a conversation from a notification, which is what the issue already said.

### What actually arrives

The shell's last 100 notifications (`~/.local/state/omarchy/notifications/history.json`, counted by sender only) are
70 Herdr, 18 `nixi-job`, 3 MeetingAI, 3 `omarchy-action`, 2 Meeting Mode, 2 Omamail, 1 Nixi and 1 Gmail in Chrome.
None are from a chat app. Google Chat has 10 direct-message spaces (`gog --readonly chat spaces list`, counted only),
so it's in use, but none of its messages reached this desktop as a notification in that window.

### A send gap that exists today

Only herdr writes are click-only. `isHerdrWrite` decides (`bridge/herdr-policy.js:7-14`), and `confirm: "click"` is set
only for it (`bridge/bridge.js:580`). So if Nixi's agent runs `gog chat messages send` or `gog gmail send` through Bash:

- in YOLO it runs with no card (`bridge/bridge.js:551`);
- in Ask a spoken "yes" approves it (`index.html:2889-2890`);
- a clicked "always" is offered and remembered for it, so later sends get no card. Herdr writes are excluded from this
  (`bridge/bridge.js:461`, `bridge/always.js:37`), but `gog` sends aren't;
- switching to YOLO approves a pending `gog` send, though not a pending herdr write (`bridge/bridge.js:903`).

That breaks the intent's rule that a voice yes never sends. It doesn't depend on this slice, and the fix is small:
treat a `gog` send as a herdr write is treated. See open question 2.

## Design

**Recommended: not now.** No chat app on this desktop can be replied to from a notification. Only Google Chat has a
safe send path, and none of its messages reached this desktop in the last 100 notifications. Building a reply path
would add a new Google Chat reader, a new card and a new send route for messages the user doesn't see here. #212 is
closed with this spec as the record, and is reopened when one of these changes:

- the user reads Google Chat on this desktop and wants replies (open question 1);
- Omarchy turns on `inlineReplySupported` and passes the reply through its socket, so an app's own reply can be used;
- another chat app gets a real API path here, such as a Slack token.

**If the user picks Google Chat,** the design is this, and it reuses #210's reply card:

1. **The conversation comes from Google, never from the notification.** A Chat notification only shows a "reply" chip.
   Clicking it makes the server run `gog --readonly --account <account> --json chat messages list` on the
   direct-message spaces, with the account named in settings. The server keeps the list. The card shows the newest
   incoming messages: sender, space, time and their first words. The user clicks one, and the page sends back only its
   position in the server's list, never a space or thread. Nothing from the notification is used to match.
2. **The user writes the words.** They type them in the card, or dictate them into the box, where dictation only fills
   the box. No agent drafts the reply in this slice, so the message text never reaches a model.
3. **The card binds everything.** When the user presses "Review", the page posts the words. The server checks that
   the thread belongs to the space, then stores `{nonce, account, space, thread, text}` under a random nonce
   (`secrets.token_urlsafe`). The card then shows the account, the sender, the space's display name, the thread and
   the exact words. Any edit makes the old nonce invalid, and the user has to press "Review" again. The page sends back
   only the nonce, with the server's existing token (`server.py:63`).
4. **Only a click sends.** The server takes the nonce out of the store under a lock, checks its age, and only then
   runs, as a list and never through a shell, `["gog", "--account", account, "--no-input",
   "--enable-commands-exact=chat.messages.send", "chat", "messages", "send", space, "--thread=" + thread,
   "--text=" + text]`. The `=` form keeps text that starts with `-` from being read as a flag. So two clicks can't
   both send. A nonce works once and goes after 5 minutes.
5. **The card shows what Google returned,** "sent" with the message's name, or the error, not the click. A timeout
   shows "not sure it was sent, check Chat", and it's never retried.
6. **Nothing is logged:** no text, no names and no space IDs. That matches the inbox's rule (`server.py:2161-2163`).

That would add one read route, one send route, a card section and their tests to `app/server.py` and
`app/static/index.html`. It should come after #210, because it reuses #210's card and its send guard.

## Alternatives rejected

- **Turning on inline reply in the shell.** That's upstream Omarchy code. It would also need the reply text to go back
  through the socket. Of the apps here, only Telegram might use it, and that's unverified. Revisit if Omarchy adds it.
- **Matching a notification to a conversation by sender name or text.** Any local program can send a notification with
  any name (#215 spec), so a reply could go to the wrong person.
- **Sending through the app's window,** with typed keys, `wtype` or a scripted browser. It can't be bound to a
  conversation, and it types into whatever has focus.
- **Discord or WhatsApp through unofficial clients.** That's against their terms, and it puts the user's account at risk.
- **A new Slack or Teams login just for this.** That adds a stored token and a new secret. Nothing shows the user
  needs it, since none of these apps' notifications reached this desktop.
- **Letting Nixi's agent send with `gog` from a chat request.** That's the gap above: the agent's own words and target
  would decide the destination, and in YOLO nothing asks.

## Risks

- **Not now:** none to the code. The cost is that the intent's "reply to chat apps" stays undone. The send gap is
  there either way until open question 2 is decided.
- **If Google Chat is built:**
  - Messages from the API are untrusted, as message text already is. They're shown as text, never as HTML. The
    summary and logging rules of #210 apply.
  - Picking the wrong message from the list sends to the wrong person. The card names the sender and space plainly,
    and the send button repeats the sender's name.
  - Reading 10 spaces costs API quota and a few seconds. It runs only on a click, never on a timer.
  - A `gog` token for the wrong account would send as that account, so the card shows the account.

## Verification

- **Not now:** this spec is approved, and #212 is closed linking it. The evidence above can be rerun read-only:
  `grep -n Supported` on the shell's `Service.qml`, the row fields at `Service.qml:705`, `gog chat messages send --help`,
  and the sender count of the shell's history.
- **If Google Chat is built:** tests in `tests/test_inbox.py`, with `gog` mocked, check that:
  - the send argv is exactly the stored values, as a list;
  - text with a leading `-`, quotes, newlines and emoji arrives unchanged in the argv (and, by hand, in Chat);
  - a reused, expired or unknown nonce sends nothing, and two clicks at once send once;
  - a thread from another space is refused;
  - edited words need a new nonce;
  - a page-supplied space, thread or account is ignored;
  - `--readonly` is on every read and `--enable-commands-exact` is on the send;
  - nothing is logged.
  A page test checks that dictation fills the box and never sends. A by-hand check on p620, with a test DM to the
  user's own second account, covers the rest.

## Open questions

1. **Do you read Google Chat on this desktop, and do you want to reply from Nixi?** Recommended: no, so #212 closes
   as "not now". If yes, the Google Chat design above goes to a plan after #210.
2. **Who closes the `gog` send gap?** Today the agent can run `gog gmail send` or `gog chat messages send` on a
   spoken yes, after a remembered "always", or with no card in YOLO (`bridge/bridge.js:461`, `:551`, `:580`, `:903`,
   `bridge/always.js:37`). Recommended: #210, since it adds the first `gog` send.
   - `gog` has many ways to send, with aliases: `gmail send`, `reply`, `reply-all`, `forward`, `drafts send|post`, and
     `chat messages send|create|post`. A list of send commands would miss some, so do what herdr does: any command that
     mentions `gog` needs a click, in every mode. The cost is that the agent's `gog` reads, such as calendar, need a
     click too.
   - Add a separate check, such as `needsClick`, and use it everywhere `isHerdrWrite` guards today: YOLO, the card,
     "always", remembered approvals and switching to YOLO. Don't widen `isHerdrWrite` itself, because that also calls
     `auditSend`, which writes up to 500 characters of the command, including the message, to `sends.log`
     (`bridge/bridge.js:750-766`).
   - It's a best-effort check, like herdr's (`herdr-policy.js:6`): a script, a variable or a direct HTTP call with
     `gog`'s token gets past it. Fully closing that would mean the agent never holds a token that can send. That's a
     larger change, and it's for #210 to weigh.
3. **Minor, out of scope:** the shell stores the full `rawBody` and `execArgv` of every notification in
   `history.json`. That's Omarchy's design, not Nixi's, and is only noted here.

Their findings don't approve anything. Codex reported `gpt-6.1-sol`. agy's JSON reports no model. Codex's first run

**Confirmed and applied:**

- Both: the `gog` send gap is real. agy restated the draft's finding.
- Codex: the gap reaches further than the draft said. "Always" and switching to YOLO also let a `gog` send through
  (`bridge.js:461`, `:903`, `always.js:37`).
- Codex: widening `isHerdrWrite` would log message text through `auditSend` (`bridge.js:750-766`). A separate check is
  proposed.

- Codex: the nonce has to be claimed under a lock before `gog` runs, or two clicks could both send.
- Codex: edits need a fresh nonce through a "Review" step. Reads need the same `--account` as the send. The thread has
  to belong to the space.
- Codex: `--text=` keeps text starting with `-` from being read as a flag. The tests now cover it.
- Codex: some claims went further than the evidence. They now say the shell doesn't offer inline replies, not that no
  app sends one; the inventory is what this check found; and Messenger, which `Inbox.CHAT` knows, has its own row.

**Refuted:**

- agy: the spoofed-sender risk is "high". The Google Chat design takes the conversation from the API and never from
  the notification, so a spoofed notification can't choose who gets the reply.
- agy: matching any `gog` command would stop the UI fetching conversations. Nixi's server runs `gog` itself, as the
  calendar does (`server.py:1486`), and the bridge's check applies only to the agent's tool calls. The cost to the
  agent's reads is stated.
- agy: matching on `gog` misses aliases. It catches every alias. A list of send commands, which agy proposed instead,
  is what would miss them.
- agy: `gog` could be extended for Slack. `gog` is a Google Workspace CLI.

**Not verified:** a real `gog chat messages send` on p620, including how v0.48.0 handles `--text=-x`; the server's
token and origin checks for a new send route; and whether the user reads Google Chat anywhere.
