# Spec: Location — Home, Work and where I am now, set by me

## What exists today (checked)

- **`~/.local/state/omarchy/settings/weather.json`** holds
  `{"name", "latitude", "longitude"}`. It's upstream Omarchy's format, owned
  by `omarchy-weather-location` (`--set <name> [lat,lon]`, `--clear`).
  - **A missing file means auto-detect from IP.** wttr.in guesses the city.
- **The bar's weather panel already has a city picker** (upstream
  `shell/plugins/panels/weather/Panel.qml`). It searches Open-Meteo's
  geocoder and saves through `omarchy-weather-location --set`. So a location
  can already be set without a terminal. It's just hard to find, and it's
  called "weather".
- **The companion** reads the weather with `omarchy weather status`
  (`Ambient`, `app/server.py:1048`). It knows no location, and `maps_url`
  (`app/stages.py:250`) sends no start point.
- **Hosts:** p620 is wired (`ethernet: LAN`). razer is on Wi-Fi, and its
  network today is named `home`.

## Design

### 1. Two files: the current place (unchanged) and your places (new)

- **`weather.json` stays the current place.** Its format and owner are
  unchanged, so the bar, the weather scripts and the bar's picker keep
  working untouched.
  - The rule that follows from it: **the file existing means you chose this
    place** (in the picker, a command, the Now switch or a Wi-Fi rule). **A
    missing file means an IP guess.** That one rule drives the privacy
    constraint below.
  - Places the Wi-Fi rule writes carry an extra `"source": "wifi"` key. The
    upstream readers only read `name`, `latitude` and `longitude`, so they
    ignore it.
- **New `~/.local/state/omarchy/settings/places.json`:**
  ```json
  {"home": {"name": "Oxford, UK", "latitude": 51.75, "longitude": -1.26},
   "work": {"name": "London EC2", "latitude": 51.52, "longitude": -0.09},
   "wifi": {"home": "home", "OfficeNet": "work"}}
  ```
  - `home` and `work` are optional, and coordinates are optional within each.
  - `wifi` maps a network name to `home` or `work`.
- **Migration:** if `weather.json` exists and `places.json` has no `home`,
  the first run copies the stored place into `home`. Your place carries over,
  as the intent requires.

### 2. `nixarchy-location`: one command that owns your places (nixarchy repo)

A small bash command in `pkgs/`, packaged like `doctor.sh`, with `jq` and
`nmcli`:

| Command | Does |
|---|---|
| `nixarchy-location` | prints the current place and how it was set: `Oxford, UK (home)`, `(you)`, `(wifi: home)` or `Auto: Reading (approximate)` |
| `nixarchy-location set home\|work <name> [lat,lon]` | stores Home or Work |
| `nixarchy-location now home\|work\|auto` | writes Home or Work into `weather.json`, or clears it (auto) |
| `nixarchy-location wifi link home\|work` | links the Wi-Fi network you're on now to Home or Work |
| `nixarchy-location wifi unlink <network>` | removes a link |
| `nixarchy-location apply` | applies the Wi-Fi rule once (see §3) |
| `nixarchy-location --json` | everything above as JSON, for the companion |

- **Writes are atomic** (temporary file, then `mv`) and use the same
  coordinate check as `omarchy-weather-location`.
- **Setting Home or Work never sends anything anywhere.** Turning a name
  into coordinates is done by the caller: the companion's settings use the
  same Open-Meteo search the bar's picker already uses. The command itself
  stores what it's given.

### 3. Where am I now: Wi-Fi recognition (laptops)

- **A user service, `nixarchy-location-watch`**, runs `nmcli -t monitor`
  and calls `nixarchy-location apply` whenever a connection comes up. It is
  event-driven, so nothing is polled.
  - It's started only when `places.json` has at least one `wifi` link. A
    wired desktop never runs it.
- **What `apply` does:**
  - **on a linked network:** write that place to `weather.json`, with
    `"source": "wifi"`;
  - **on an unlinked network:** if the current `weather.json` came from Wi-Fi
    (`"source": "wifi"`), clear it, so the place falls back to an approximate
    IP guess. A place you chose by hand (no `source`) is never touched. So
    the laptop doesn't claim "Home" in a café, and it doesn't undo your
    choice.
- **A desktop (p620):** "Now: Home" writes Home once and stays. This is the
  "pin" from the intent, set in the settings and not in nixos_config (open
  question 3, the suggested answer).

### 4. The companion (nixoarchy-snowflake)

- **Reading:** `location()` runs `nixarchy-location --json` with a 2 s
  timeout and caches it for 60 s. If the command is missing, it reads
  `weather.json` and `places.json` directly, which covers older nixarchy
  installs. It never touches the network: the IP guess is the weather's
  business.
- **Settings, a new "Location" section:**
  - **Now:** Home, Work or Auto, with the resolved line under it.
  - **Home** and **Work:** a text field with suggestions (Open-Meteo,
    `count=5`). Picking one stores the name and its coordinates; typing a
    name without picking stores the name only.
  - **Wi-Fi** (shown only when a Wi-Fi device exists): "Link <network> to
    Home / Work", plus the existing links with ✕ to remove each.
  - Every change goes through `nixarchy-location`.
- **The agent line.** When `weather.json` exists (a place you chose), the
  note gets one line: `The user is in <name>.`
  - The note also says that for directions to the user's home or work, the
    destination is `@home` or `@work`. The agent never sees the addresses.
- **The map stage:**
  - **`dest` `@home` or `@work`:** the server swaps in the stored place.
    - If it isn't set, the card says "Set Home in Nixi's settings", with a
      **Settings** button and no Google button.
  - **Start point:** `maps_url` gains `&origin=<current place>`, but only
    when `weather.json` exists. Coordinates are used when present, otherwise
    the name.
  - **The footnote** reads "From <place>" in that case, and stays "Google
    Maps picks the way and the start" otherwise.
- **Never sent:** an IP guess, `places.json` itself, and the Wi-Fi network
  names.

### 5. The nixarchy menu

- **Setup → Location** opens the bar's weather panel, which has the existing
  picker, for people without Nixi.
- A one-line hint in the panel or in the docs points to
  `nixarchy-location set home …` and to the Wi-Fi links.
- The menu itself is not rebuilt; the Home/Work/Wi-Fi interface lives in
  Nixi's settings (open question below).

## Alternatives rejected

- **A separate Nixi-only location.** The bar and Nixi would disagree; the
  intent rules it out.
- **Putting Home, Work and the Wi-Fi links inside `weather.json`.** Upstream
  owns that format, and its picker overwrites the whole file on save, which
  would wipe them.
- **A NetworkManager dispatcher script.** It runs as root, system-wide, so it
  would have to find each user's home and write their files. A user service
  running `nmcli monitor` stays inside the user's session.
- **geoclue or Google's Geolocation API.** Ruled out of scope by the intent.
  The Google API also needs a paid key and sends nearby Wi-Fi addresses
  away.
- **Sending `destination=Home` to Google and letting it resolve your saved
  home.** It's unverified (open question 2 in the intent). It only works
  when you're signed in, and it would quietly fail anywhere else. `@home`
  resolved by us works everywhere. If the test shows Google does resolve
  `Home`, the unset-Home card could offer it as a second button, but nothing
  depends on it.
- **The companion polling the Wi-Fi network.** Users without Nixi need it
  too, and polling wakes the CPU for nothing.

## Risks

- **The bar's picker and the Wi-Fi rule both write `weather.json`.** Picking
  a city removes `source`, so the Wi-Fi rule leaves it alone until you're on
  a linked network again. That's intended: "you chose" wins until a network
  you linked says otherwise.
- **Network names aren't unique.** Many homes have a network called `home`.
  A link only applies to a network the user linked on their own machine, so
  the worst case is a café with the same name being read as Home. That's
  acceptable, and it's shown in the settings so the user knows.
- **`nmcli monitor` output format.** Read with `-t` (terse). If the format
  changes, the service fails to recognise networks, and the place falls back
  to what the user set or to auto. Nothing breaks.
- **An upstream Omarchy update** could change `weather.json`.
  `nixarchy-location` reads it through `omarchy-weather-location` and writes
  the same keys, and a test pins the format.
- **Hosts:** p620 (desktop, Now = Home) and razer (laptop, Wi-Fi). Both
  deploy the usual way.

## Verification

- **`nixarchy-location`** (bash tests with a temporary `HOME` and a fake
  `nmcli` on `PATH`):
  - `set`, `now` and `--json` round-trip;
  - migration copies an existing `weather.json` into `home`, once;
  - `apply` on a linked network writes the place with `"source":"wifi"`;
  - `apply` on an unlinked network clears only a `"source":"wifi"` place and
    leaves a hand-picked one;
  - a bad coordinate is refused and the file is unchanged;
  - `omarchy weather location` still prints the place after each write.
- **Companion** (unit tests):
  - the agent note has `The user is in …` only when `weather.json` exists;
  - `@home` resolves to the stored place, and an unset Home gives the
    "Set Home" card with no Google token;
  - `maps_url` has `origin` only when a place is set;
  - nothing in the note or URL comes from an IP guess.
- **Page:** the Location section in the GPU-free headless preview, with the
  Wi-Fi block hidden when there's no Wi-Fi device.
- **Live:**
  - **p620:** set Home, then switch Now to Home. The bar's weather shows Home,
    and "directions to Oxford station" opens Google Maps from Home.
  - **razer:** link `home` to Home. Turning Wi-Fi off and on brings Home
    back, and a phone hotspot (unlinked) goes to "Auto (approximate)".
  - "Directions home" opens your Home without the agent seeing the address.
