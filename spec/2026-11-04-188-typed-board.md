# Spec: A question typed while the mic is open gets its board

Code: `olafkfreund/nixoarchy-snowflake`. Lines are at `origin/main`, `f6462c2`,
after #177.

## Design

Three small changes do the work. A dropped recording stops counting as a
recording straight away, everything that means "I'm typing or clicking now"
drops it, and the server keeps the follow-up window shut while the box is open.
The `rec` check in `stageShow` (`app/static/index.html`, line 2578) stays, so a
board that arrives while you're really listening is still a caption (decision 3).

### 1. A cancelled recording is gone at once (`index.html`)

`stopRec(true)` (line 2238) clears `rec` immediately and clears its own caption:

```js
function stopRec(cancel){ const r=rec; if(!r) return; r.stopping=true;
  if(cancel){ r.cancelled=true; rec=null; if(r.mode!=='approve'){ setYou(''); capQuiet(); } }
  if(r.opened) post('/api/listen/stop',{cancel:!!cancel}); }
```

`startRec` (lines 2212-2236) then ignores whatever a cancelled recording still
reports:

- `open`: sets `r.opened` and posts the stop as today, but no "listening…" and
  no sound if `r.cancelled`.
- `speech`: no "…" if `r.cancelled`.
- `note`: no clipping message if `r.cancelled`.
- `transcribing`: unchanged, so `transcribing` stays true until the stream ends
  (see "Settled").
- After the stream ends, `if(r.cancelled) return mode==='approve'?'':null;` goes
  before the `approve` line and the `err` line. The text is discarded, and so is
  a mic error, including the silent-mic one the server sends before it checks for
  a cancel (`server.py`, line 2878).
- The `if(!r.cancelled)` around "didn't catch that" (line 2235) can no longer be
  false there, so it goes. When the server gives up by itself, `r.cancelled` is
  false, so "didn't catch that" still shows for voice.

Esc (line 3848), hiding (lines 3023 and 3695) and approvals (lines 2772 and 2777)
already call `stopRec(true)`, so they get all of this. That is decision 2.

### 2. Typing or clicking drops the recording (`index.html`)

- **The box opens.** `showAsk` (line 2674) calls `endListening()` and starts the
  hold from part 3, only when the box wasn't already open. `endListening`
  (line 3025) already spares an `approve` recording and closes the follow-up
  window. Every way into the box goes through `showAsk`: Return, a printable key
  (lines 3863-3864), and the menu's `/cd` and Look (lines 3021-3022).
- **Any question is sent.** `send` (line 2788) adds this after its empty-text
  check:

  ```js
  if(!opts.follow&&((rec&&rec.mode!=='approve')||follow)) endListening();
  ```

  That covers Run (line 2609), Again (line 2958), Quick actions (line 2969) and
  `remember`/`forget` with one line, and it closes an open follow-up window as
  well. `startRec` clears `rec` before its own `send`, and a question heard in
  the follow-up window has `opts.follow` set, so neither cancels itself.
- **Anything that waits first.** These three call `endListening()` before they
  wait, because a recording that ended during the wait would send its speech
  first:
  - "continue this chat", before `/api/resume` (line 2959). It sends nothing
    itself, so this is its only drop;
  - a Quick action with an attachment, before `shoot` (line 2968);
  - the menu's Look, before `shoot` (line 3022). If the capture fails, the box
    doesn't open and the recording is still dropped.

### 3. The follow-up window stays shut while the box is open

The server gets one flag and one `/api/follow` action (`app/server.py`):

```python
held = False                             # the ask box is open: no follow-up window
...
def talking_until(cls, end, follow=True):
    cls.speaking_until = end
    if not follow or cls.held:
```

```python
if p == "/api/follow":
    b = json.loads(self._body() or b"{}")
    if b.get("act") == "hold":
        Wake.held = bool(b.get("on"))
        if Wake.held:
            Wake.end_follow("cancel")        # (after the flag: a window scheduled either side of it stays shut)
    else:
        Wake.end_follow("finish" if b.get("act") == "finish" else "cancel")
    return self._json({"ok": True})
```

`talking_until` (line 3090) is the only place that opens a window, from both
`Speaker` (line 4169) and `/api/speaking` (line 6234). So nothing else has to
learn about the flag: `window_open`, `should_run` and `check` all read
`follow_until`. The hold also closes any window already scheduled, because
`Speaker` sets the window before his sentence plays. Ending the hold reopens
nothing. The window next opens the next
time he talks, as today.

On the page, `showAsk` posts `{act:'hold',on:true}` and `hideAsk` (line 2675)
posts `{act:'hold',on:false}`, each only when the box really changes state.
`hideAsk` is called from many places when the box is already closed. The page
also posts `on:false` when it loads, next to `events()` (line 4003), so a reload
with the box open can't leave the flag stuck.

The `wake` handler (line 2162) adds a backstop:
`if(ev.follow){ if(busy||ask.classList.contains('on')) return; …`. It covers the
moment before the hold reaches the server, and a server restart while the box is
open. "Hey Nixi" uses a different branch (line 2164), so it works as today.

### 4. Cancelling the follow-up window reaches speech being transcribed

`Wake.check` decides `follow` before it transcribes (`server.py`, line 3210) and
publishes after (line 3237), so a cancel in between does nothing. The test from
line 3210 becomes a small `in_window(started)` method, and `check` runs it again
afterwards:

```python
elif follow and cls.in_window(started):          # (cancelled while we were transcribing)
```

`follow_from` and `follow_until` don't change when a window simply runs out, so
speech that began inside the window still counts, however long Whisper takes.
They change when something closes the window or he talks again. If a new window
opened meanwhile, `started` is before its `follow_from`, so the old speech is
dropped too. The same re-check also drops the speech if a turn has started
meanwhile (`ST.lock`).

## Settled

These are the two items the intent left for this spec.

- **Does cancel clear `rec` immediately? Yes.** The stream can take a while to
  end: at least one 0.1 s mic read, and as long as Whisper needs if it has already
  started. Until then the page would treat a dropped recording as live: `stageShow`
  declines, a click tries to stop it again, and `wake` is ignored. Waiting would
  break the promise that a board shows while the mic is shutting down.
- **`transcribing` does not clear early.** Whisper can't be interrupted, and the
  server holds `Listen.lock` until it finishes. A new recording would wait 2 s and
  then fail with "mic busy" (line 6366). So the existing `rec||transcribing` check
  in `startRec` (line 2213) keeps the mic from restarting until then. `stageShow`
  doesn't read `transcribing`, so boards are unaffected.
- **What does cancelling the follow-up window do to speech being transcribed?**
  Today, nothing: the speech is still sent. After part 4 it's dropped, unless it
  was "hey Nixi", which is a clear request. Speech not yet being transcribed is
  already dropped by `cut` (line 3170).

## Alternatives rejected

- **Remove `rec` from the `stageShow` check.** That fixes the board in one word,
  but slips would open over someone talking, which decision 3 rules out. It also
  leaves the stray questions and the caption damage.
- **Check `rec.cancelled` in `stageShow` and leave `rec` set.** Every other
  reader of `rec` (`mood`, the click and Esc handlers, `wake`, idle) would need
  the same check.
- **Only ignore follow-up speech on the page.** The server would still open the
  mic, run Whisper and show him listening while you type, which isn't "stays
  shut".
- **Add a hold check to `window_open`, `should_run` and `check`.** That's three
  places for what `talking_until` does in one.
- **Give each recording an id for `/api/listen/stop`.** It closes only the
  narrow race under Risks, which takes a key press within milliseconds.

## Risks

All of these apply to p620 and razer alike.

- **Stray key.** A key pressed while talking, or while holding Space, throws that
  speech away. The user accepted this in decision 1.
- **He looks like he's thinking while you type.** If the speech was already being
  transcribed, `mood` shows thinking until Whisper finishes (line 1339), and a
  click or Space does nothing until then. It lasts as long as the transcription.
- **A second Esc during that time goes further.** With `rec` already clear, it
  falls through to the next Esc action, which can hide Nixi. Today it would cancel
  the recording again, which does nothing.
- **Stale stop.** `/api/listen/stop` stops whichever recording is current. A stop
  for an old recording that arrives after a new one started would stop the new one.
  It needs a new recording within milliseconds of the drop. The result is a lost
  recording, not a stray send.
- **Mic restart in the gap.** If the server has passed its cancel check and the
  `transcribing` event hasn't reached the page, a new recording could get "mic
  busy". Same milliseconds.
- **Hold posts out of order.** Opening and closing the box within milliseconds
  could leave the flag on. The result is no follow-up window until the box next
  opens and closes, or the page reloads. Nothing is sent by mistake.
- **Approvals change slightly.** `rec` now clears at once for `approve` recordings
  too, so the next approval's voice answer can start while the old recording shuts
  down, and the server's lock handles the overlap (line 6362). If the old one was
  already transcribing, the next one still gives up on voice, as it does today,
  and can be answered by click. `startRec` ignores the text of a cancelled
  `approve` recording. Its caller `askAloud` already ignored it when the approval
  had moved on (line 2764).

## Verification

**Page tests**, added to `tests/stages_fit.mjs` (headless Chromium, run by
`tests/test_stages_fit.py`), with `window.fetch` stubbed to give a controllable
recording stream (`post` is a `const`, line 1006; the existing tests stub `fetch`
too):

1. Mic open, `showAsk`, then a `stage` event before the stream ends: `rec` is
   null and the slip opens.
2. Same, with the `stage` event sent while the mic is open and the box closed:
   caption, no slip (decision 3 is unchanged).
3. After the drop, the stream sends `open`, `speech`, `transcribing`, `text`, or
   `error`: the caption doesn't change, and `send` isn't called.
4. Esc and `nixiHidden` during `transcribing`: the text isn't sent.
5. A recording with no drop gets no speech and ends: "didn't catch that" still
   shows. One with text still calls `send`.
6. An `approve` recording with `showAsk`: `rec` is untouched and its text still
   returns.
7. Mic open, then `send`, and "continue this chat" with a delayed `/api/resume`:
   `rec` is null before the response, and the restored caption stays.
   Quick action with an attachment and a delayed capture, while a recording would
   finish during it: only the action is sent. The same for Look.
   Run during a follow-up window: a `cancel` post goes out. A `send` with
   `follow:true`: no `cancel` post.
8. `showAsk` twice, and `hideAsk` twice: one hold post each way.
9. A `wake` event with `follow:true` while the box is open: nothing is sent. A
   `wake` event without `follow`: still acts.

**Server tests**, in a new `tests/test_follow_hold.py`, in the style of
`tests/test_floor_wiring.py`:

1. `held` on, then `talking_until(end)`: `follow_until` is 0 and `window_open` is
   false. `held` off, then `talking_until`: it opens.
2. `/api/follow` with `act:"hold",on:true` sets the flag and closes a window
   scheduled before it. `on:false` clears the flag and doesn't set `cut`. The old
   `finish` and `cancel` act as before.
3. `Wake.check` with `transcribe_pcm` stubbed to close the window partway: no
   `wake` published. Same with the window simply running out partway: `wake`
   published. A new window opening partway: no `wake` published. "Hey Nixi" with
   the window closed partway: `wake` published.

**Whole suite:** `python3 -m pytest tests` passes, or at least fails only where it
already fails on `f6462c2`.

**Live on p620,** by the user or the lead, after deploy:

1. Click Nixi, press Return, type "show me the latest world news": slip appears.
   Repeat for the fleet board.
2. Click Nixi, press Return, and wait 10 seconds without typing: no "didn't catch
   that".
3. Click Nixi, say a question, and let it finish: answer as today.
4. Ask something, and while he answers press Return and wait with the box open:
   no listening bars when he stops. Esc, then ask again: the follow-up window works.
5. Say "hey Nixi" with the box open: he responds.
6. Trigger an approval and answer it by voice.
