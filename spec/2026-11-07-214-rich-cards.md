# Spec: rich notification cards

Nixi's code is in `olafkfreund/nixoarchy-snowflake` at `origin/main` `8f2275e`. The shell side is the user's own patch
`pkgs/omarchy/903-notification-delegate.patch` in `olafkfreund/nixarchy` at `origin/main` `6cd4e33`, applied to
Omarchy's `shell/plugins/notifications/Service.qml` (`pkgs/omarchy/default.nix:2022`). Every added line of that patch is
in the installed `omarchy-edge-20261104-cc99764` shell, so the store copy and `main` agree. Line numbers are from those
commits, so re-find them by name. This repo, `nixi-nixarchy`, has no notification code: its `Ask.qml` overlay never
sees a notification.

## What the shell hands over today

Investigated read-only, from the code and the installed store paths. Nothing was restarted, and no notification was
read.

| What | The shell has it | Nixi gets it | Evidence |
|---|---|---|---|
| Summary | up to 2048 chars | plain text, cut to **200** by the shell, then **120** by Nixi | `Security.js:4`; patch `:114`; `server.py:2252` |
| Body markup | yes: `bodyRich`, a safe subset | no: `bodyLine`, markup stripped to one line, cut to 200, then 120 | `Store.js:120-121`; `Markup.js:96-113`; patch `:115`; `server.py:2252` |
| Image | yes: a checked local path, or `image://qsimage/…` pixels held in the shell's own process | no | `Store.js:19-27`, `:117`; `Security.js:114-131`; patch `:114-115` |
| Named actions (buttons) | yes, up to 16, invoked by identifier | **no: a row with buttons isn't handed over at all** | patch `:111-112`; `Service.qml:994-1013` |
| `--action` commands (`execActions`) | yes, up to 3 argv lists | no: those rows stay shell cards | patch `:112`; `Security.js:74-92` |
| The click | the sender's `default` action, window or web address | yes, through `activateKey` | patch `:177`; `server.py:6215` |

So **the 120-character cut is Nixi's own**, in `Inbox.rows` (`server.py:2252`), on top of the shell's 200 (patch
`:114-115`). The page then cuts a chat line to its first six words and 90 characters (`index.html:2431`).

The shell keeps buttons back on purpose. nixarchy #1558 ("delegated rows lose their action buttons") chose its option 2,
"don't take rows that carry non-default actions", in `0133734`. Its option 1, carrying the actions over and adding a
`notifications.invokeAction(key, action)` IPC, is what this slice needs.

**Answer: the shell can't hand over markup, images or actions today.** The intent says that if it can't, the slice adds
nothing. The gap is in the user's own patch, not in upstream Omarchy, and the shell already has every piece it needs.
So this spec proposes a small change to patch 903. The user chose that change over closing #214 (2026-11-07).

## Design

### 1. Pin today's behaviour first

The intent requires it. The page tests from #215 (`tests/notify_fit.mjs`) and `tests/test_inbox.py` already pin the
row, the queue, grouping, the envelope, the bubble, sound, speech, clicks and the hand-back. They're re-run unchanged
before any change. New cases pin what this slice must not change: a row with no image and no buttons still gets
today's row, cut to 120, and today's `notify_details`, secret and one-time-code checks.

### 2. The shell hands over buttons, an image and the markup (nixarchy, patch 903)

- **Only when asked.** A new IPC, `delegateRich(ms)`, does what `delegate(ms)` does (patch `:147-166`) and also sets
  `richLease`. `delegate(ms)` clears it. Only while `richLease` is set does the shell queue buttoned rows or add the new
  fields. So an old Nixi, which calls `delegate`, keeps today's behaviour, with no buttons lost (#1558). A new Nixi on
  an old shell gets no reply to `delegateRich`, falls back to `delegate`, and shows today's rows.
- **Eligibility** (patch `:106-122`). While `richLease` is set, `actionsOf(key, refsRevision).length === 0` becomes
  "every named action can be carried": at most 3, each identifier 1-64 printable characters, with none of
  `\x00-\x1f` or `\x7f`, which also rules out the IPC's `\x1e` and `\x1f`. A row with more, or with an odd
  identifier, stays a shell card, as today. **`!row.execActions` stays**: a row whose buttons run commands is never
  handed over.
- **The queued row** gains three fields:
  - `actions: [{id, text}]` from `actionsOf()`, which already drops `default` and `settings`, with `text` cut to 40;
  - `image`: `row.image` only when it isn't a `qsimage` URL, so only a path that already passed
    `Security.localImagePath`, else `""`;
  - `rich`: `String(row.bodyRich).slice(0, 600)`.
- **A buttoned row is held 30 seconds**, not 12, after it's handed over (patch `:158`), so a button on a 7-second card
  always finds it.
- **New IPC** next to `activateKey` (patch `:177`):

  ```qml
  function invokeKey(key: string, id: string): string {
    if (!service.liveKeys[key]) return "none"
    if (!service.actionsOf(key, service.refsRevision).some(function(a) { return a.id === id })) return "none"
    if (!service.invokeSenderAction(key, id)) return "none"
    service.closeToast(key, "activated")
    return "ok"
  }
  ```

  `invokeSenderAction` (`Service.qml:1029`) only calls `invoke()` on an action the live sender itself offered. That
  sends the D-Bus `ActionInvoked` signal back to that sender, so a button runs nothing in the shell or in Nixi.
  `closeToast` on a key with no card goes to `finishClose` (`Service.qml:857`), as `dismissKey` does.
- **The click on the card body is today's.** `activate()` still runs a row's `execArgv` (`omarchy-exec-argv`, patch
  `:138`), which any session-bus sender may set (`Security.js:50-53`). That's how a row click and a shell card click
  work today, and this slice doesn't change it.
- `tests/session.nix`, which already tests the lease, gains these cases:
  - under `delegateRich`, a buttoned row is handed over with its actions;
  - under `delegate`, it isn't;
  - an `execActions` row and a row with 4 actions are never handed over;
  - `invokeKey` fires the named action (`notify-send -A more=… --wait` prints `more`, the #1558 repro);
  - an unknown id or key returns `none`;
  - a `qsimage` image is handed over as `""`;
  - a buttoned row is still live after 20 seconds.

### 3. Nixi checks it and builds the card (`app/server.py`)

`Inbox.tick` calls `delegateRich`, and `delegate` when that gets no reply. `Inbox.CAP` goes from 64 KiB to 1 MiB.
The worst reply is 32 rows of about 1,600 characters, which is under 310 KB even if JSON writes every character as a
6-byte escape. Today an oversized reply is dropped after the shell has already cleared its queue
(`server.py:2198`, `Service.qml:1527-1528`), so those rows would never show.

`Inbox.rows` keeps today's row as it is, with `summary` and `body` cut to 120. A row also gets a `card` only when it has
an image or buttons. The steps run in this order:

1. **Markup** is parsed by a small tokenizer, `Inbox.runs(rich)`. It finds tags in the raw `rich` first, then
   decodes `&lt;`, `&gt;`, `&amp;` and `&quot;` in the text between them only, so decoded text is never parsed again.
   - It accepts only the tags `bodyRich` can contain: `b`, `strong`, `i`, `u`, `s` (drawn plain), `br/`, and
     `a href="…"`.
   - An unknown, unclosed or cut-off tag is dropped and its text kept. A closing tag with no opening tag is dropped.
     There's no nesting depth beyond the three flags `b`, `i` and `u`.
   - The output is a list of `{t, b, i, u, host}` runs, at most 600 characters of text and 64 runs. `host` is the
     link's host from `urllib.parse`, kept only for `http`, `https` and `mailto`. The page never gets the `href`.
   - There's no `code`, because the shell escapes `<code>` into literal text (`Markup.js:6`).
2. **The privacy gate** checks the whole card before any of it is kept. The check text is the summary, the decoded
   text of every run and every button label, joined and not cut. If `notify_details` is off, or `SECRET_LINE` or
   `Inbox.OTP` matches, the row gets no card: no text, no image, no buttons.
   - Such a row with buttons goes straight back. The server calls `showKey` and doesn't publish it, so the shell shows
     its own card with the buttons, and nothing with buttons is lost. That's a Nixi setting at work, not a filter on
     the shell.
   - A code that's only in the picture can't be caught, the same as on the shell's card.
3. **The image** is read only after the gate passes, into a new `NImage` store, in memory only:
   - The server opens the path with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, so a FIFO can't block it, then checks it
     with `fstat` on that descriptor: a regular file of at most 1 MiB. It reads at most 1 MiB + 1 byte, and refuses
     anything longer. Then it keeps the bytes, so a file changed later makes no difference.
   - Only a static PNG is accepted: the signature, a well-formed `IHDR` of 1-2048 pixels each way, and no `acTL` chunk,
     which would make it an animated APNG. That rules out SVG and anything that keeps repainting.
   - Each image gets a random id from `secrets.token_hex(8)`, so it can't be guessed, and it's kept for 60 seconds,
     with at most 8 at a time. Turning `notify_details` off empties the store.
   - New route `GET /api/nimage/<id>`: the id must match `[0-9a-f]{16}` and be in the store. It serves `image/png` with
     `Cache-Control: no-store`, else 404. As with `/api/icon` (#142), an `<img>` can't send the token. The id goes only
     to Nixi's page, over its own event stream.
   - Nothing is fetched from the network, and a path never comes from the page.
4. **Buttons.** The row carries only the labels and a `rev`, which is a random token for this version of the row.
   - `Inbox.acts[key]` keeps `(rev, ids, when)`. It's capped at 64 entries and expires after 30 seconds, like
     `Inbox.origin`, and it holds no text. An update to the same key replaces it.
   - `/api/notify/act` accepts `how: "action"` with `i` a real integer from 0 to 2 (not a boolean or a string), and
     `rev`. It pops `acts[key]` only if `rev` matches, so a stale click on a replaced row does nothing. Then it calls
     `Inbox.call("invokeKey", key, id)` once.
   - Open, dismiss and expiry also pop the entry.
   - The page never sends an id, so it can't name an action. On `none` the page shows "That notification has gone."

Nothing from a card is logged, written to disk or sent to an agent, as `Inbox`'s docstring already promises.

### 4. The page draws the card (`app/static/index.html`)

- A row with `card` takes the caption row's place, as a larger plate. It shows the app icon and name, the summary, the
  runs (at most 4 lines), a 96 px image preview and up to 3 buttons. When more rows are waiting, it shows "+N", from
  `notifyQ.length`.
- It's built with `createElement` and `textContent` only. A link is drawn underlined, with its host after it when the
  label differs. It isn't clickable, so a click on a card is a click on the card.
- **It's marked seen only once it's drawn.** For a card, `notifySeen` moves from before the draw
  (`index.html:2451`) to after the buttons are in the page. In notch mode and `body.bar`, which show only today's
  row, a card row isn't drawn and isn't marked seen. A failed draw isn't marked seen either. Either way the server
  hands it back at 5 seconds (`server.py:2268-2272`), and the shell's card keeps the buttons.
- A click on the card does what a click on the row does (`notifyAct('open')`). A button posts its index and `rev`, and
  stops the click there, so it doesn't also reach the plate's open handler (`index.html:2757`). Esc dismisses.
  Buttons are click-only: no voice answer can press one, as #95 decided for sends.
- **Arrival is today's.** The hop, mood, burst lines, the sound for its kind, the envelope for mail and the chat bubble
  play as they do now. A card isn't merged into a "3 new" row, and it waits in the same queue of 8.
- **It stays 7 seconds**, not the row's 5, unless it's acted on. With the 4-second queue limit, it's gone by about 11
  seconds after the hand-over, well inside the shell's 30.
- `sendRegion` covers the card while it shows.

## Alternatives rejected

- **Adding nothing, as the intent says when the shell can't.** The user chose the patch change instead.
  It's not the recommendation, because the missing piece is the user's own patch, and #1558 already named the fix.
- **Running `execActions` from Nixi.** They're commands the sender wrote. They stay with the shell's own card.
- **Sending `bodyRich` to the page and using `innerHTML`.** It's sender text, and the intent says never as HTML.
- **Handing over the raw body and sanitising it in Nixi.** The shell already decodes stacked entities and filters links
  (`Markup.js:10-65`). Doing it twice risks the two disagreeing.
- **Writing `qsimage` pixels to a file in the shell.** It's more shell code, and it adds a file of notification
  content on disk. Senders that send image data get no preview (open question 2).
- **Serving the image by path, or by a hash of its path, as icons do.** A path the sender chose, behind a guessable id,
  on a route with no token, is a way to read local files. Random ids over bytes read once avoid both.
- **Clickable links.** It's a second way to open URLs, beside the shell's own `Security.openExternalUrl`. A click on the
  card already opens the sender's own target.
- **Nixi's own "Read it to me" and "Mute this app" buttons from the mockup.** They belong to the reading-aloud slice and
  to the reactions slice.
- **A bell prop.** The intent's "a bell rings" is today's sound for each kind. A new prop belongs to the reactions slice
  (open question 3).

## Risks

- **#1558 comes back.** Three things guard against it. Buttoned rows come only under `delegateRich`. A card is marked
  seen only once it's drawn, so a card that isn't drawn goes back at 5 seconds. And a row the privacy gate refuses
  goes back at once through `showKey`. One gap remains: if the page dies after drawing a card and before you click, the
  buttons are lost. Today that would lose the row's text in the same way.
- **The card's click runs the sender's `execArgv`**, as the row and the shell's card do today. This slice adds no
  command path, and buttons only signal the sender.
- **A spoofed sender.** Any local program can send a notification with buttons and a picture. A button only signals that
  program. Accepted, as in #215.
- **A local file named as the image.** A sender can name any path the shell's spelling check passes
  (`Security.js:98-131`), including one a sandboxed sender can't read itself. The shell's own card already shows that
  file on screen, and Nixi shows the same picture. Nixi reads it only if it's a static PNG under 1 MiB, only behind the
  privacy gate, and serves it only under a random id that goes to its own page and lives 60 seconds. The sender never
  learns the id. Accepted.
- **A large or crafted PNG.** The size, dimension, chunk and signature checks run before the webview decodes it. A
  2048×2048 picture is 16 MiB of pixels while it shows. The PNG decoder itself is the webview's.
- **Senders that send image data, not a path.** They get no preview. Which real apps do that isn't known (open
  question 3).
- **Two repos.** Either one can land first, because of the `delegateRich` handshake. A test covers each way round.
- **Timing.** The 7-second card, after at most 4 seconds in the queue, ends well inside the 30 seconds the shell
  holds a buttoned row. "That notification has gone." covers a sender that withdrew it.
- **Performance.** One static image and a few elements per card, and nothing while no card shows.

## Verification

- The pinned tests from section 1 pass before any change, and unchanged after.
- nixarchy: the flake check that runs `tests/session.nix` passes with the new lease cases from section 2.
- `tests/test_inbox.py`:
  - a card appears only with an image or buttons;
  - the gate hides text, image and buttons, sees a secret after character 120 and a secret split by `<b>`, and sends a
    buttoned row back through `showKey` without publishing it;
  - the image is read only after the gate passes;
  - `acts` holds no text, is capped, expires, and refuses a stale `rev`;
  - the act route takes only an integer `i` from 0 to 2, so `true`, `"0"`, `-1` and `3` are refused;
  - `delegateRich` falls back to `delegate`;
  - a 300 KB reply is accepted.
- New `tests/test_nimage.py`:
  - a PNG is served once registered;
  - each of these is refused: a symlink, a FIFO (without blocking), a directory, a 2 MiB file, a file that grows while
    it's read, an SVG, a JPEG, an APNG, a PNG with a broken `IHDR`, and one of 3000×3000;
  - a file changed after reading is served as it was first read;
  - an unknown id, a bad format, an expired id and an emptied store all get 404.
- `Inbox.runs`: the allowed tags, `<script>`, `<img>`, `<a href="javascript:…">`, `<a onclick>`, `&lt;b&gt;` staying
  text, unclosed and stray closing tags, a tag cut at 600, and the 600 and 64 limits.
- `notify_fit.mjs`:
  - a card's elements, with no `innerHTML` of sender text, `+N` and 7 seconds;
  - a real CDP click on a button posts its index and `rev` and doesn't open;
  - Esc dismisses;
  - in bar mode a card isn't drawn or marked seen;
  - a row with no card is unchanged.
- By hand, from the user, on p620 after both deploys:
  - `notify-send -a test -A more="Tell me more" --wait` shows a card, and its button prints `more`;
  - `notify-send -i /path/to/a.png` shows the preview;
  - a Chrome web-app message with a picture;
  - the same with `notify_details` off, which must give the shell's own card with its buttons.

## Reviews (2026-11-07)

Their findings don't approve anything. Codex reported `gpt-6.1-sol`. agy's JSON reports no model. The first Codex run
failed with `Error: No such file or directory (os error 2)`, because `agent-review` was started from another worktree.
It was rerun from this one. Each finding was checked against the code.

**Confirmed and applied (Codex):**

- A card's click can run the sender's `execArgv` (patch `:138`, `Security.js:50-53`). It's today's behaviour, so it
  stays, but "nothing runs" now covers only buttons.
- Today's page marks a row seen before it draws it (`index.html:2451`), so an old page, bar mode or a failed draw would
  lose the buttons, and the draft's rollback was wrong. Now there's the `delegateRich` handshake, and a card is marked
  seen only once it's drawn.
- The gate has an order now: parse, check the full decoded text, then read the image. The page gets no `href`, and
  turning `notify_details` off empties the image store.
- `O_NOFOLLOW` alone doesn't stop a FIFO blocking, and APNG is PNG. Now there's `O_NONBLOCK`, `fstat`, a bounded read,
  no `acTL` and a 2048 limit.
- 32 rows of 2000 characters can pass the 64 KiB `Inbox.CAP`, and the shell clears its queue first, so rows would be
  lost. Now `rich` is 600 characters and the cap is 1 MiB.
- 7 + 4 seconds against 12 left about a second. Now the shell holds buttoned rows 30 seconds, which also settles the
  draft's question about card length.
- An update to the same key could make a stale button fire the new row's action. Now there's `rev`, a strict integer
  `i`, one-shot use and `stopPropagation`.
- The tokenizer now finds tags before it decodes entities, and has stated limits.

**Refuted (agy):**

- "The page uses `innerHTML` for the body." It doesn't: `notifyShow` uses `textContent` (`index.html:2437`), and the
  spec never sends HTML. Decoding comes before `escapeAll` in `Markup.render` (`Markup.js:96-99`), so decoded
  `<script>` is escaped.
- "The card clears after 5 s, not 7." That 5 seconds is today's row. The 7 seconds is proposed.
- "The secret check runs after the 120 cut, so it leaks." Only the cut text is sent (`server.py:2252-2256`), so
  nothing past 120 leaves. The card's gate checks its full text, as Codex also asked.
- "Rows are handed over only with no extra actions." That reads today's code as the proposal.
- "Use a new D-Bus `getDelegateRows` instead of the lease." The lease exists and works, so replacing it is more code.
- The image-race finding repeats what the draft already does: it reads once and checks the content.

**Agreed by both:** the evidence table is right, and buttons can't run a command or reach an action the sender didn't
offer.

**Not verified:** which apps send image paths or pixels, Chrome's notification image format, the webview's PNG
decoder, and the native window's click region for the card. No code has been written or run.
