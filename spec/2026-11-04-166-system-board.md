# Spec: A dark system board for "system status"

Code: `olafkfreund/nixoarchy-snowflake` (the companion). File and line
references are to `main` after PR #32. The news popout (#167) is built at the
same time and shares parts 1, 2 and 6; whichever lands first adds them.

## Design

### 1. A plugin may return `gauges` (and a spoken line)

- `app/plugins.py:702` accepts `got["kind"] in ("facts", "gauges", "headlines")`
  (headlines: #167). Everything else is still refused with "it gave something
  Nixi can't show".
- **Every plugin kind may carry `say`** (≤ 200 characters, no control
  characters, checked by `_str`). `plugin_stage()` (`app/server.py:4631`)
  returns `st.get("say") or "Here you go."` in place of the fixed
  "Here you go." (`server.py:4648`). `say` is spoken only: it is dropped
  before the stage goes to the page or the store, and it is never added to a
  prompt or a log (the existing rule for plugin output, `server.py:4633`).
- `facts` gains `say` too (same check), so existing plugins can use it.

### 2. The `gauges` kind (`app/stages.py`, `validate()` at ~line 76)

A general kind: hosts, each with meters, badges and short lists. v1 plugins
send one host; up to six are accepted so #168 needs no format change.

```json
{"v": 1, "kind": "gauges", "title": "System status", "say": "All fine. One failed service.",
 "source": "this computer", "live": true,
 "hosts": [{"name": "p620", "state": "up",
   "badges": [{"k": "gen", "v": "2944 · 26.11.20261101"}, {"k": "up", "v": "3 days 4 h"}],
   "meters": [{"label": "CPU", "pct": 18, "text": "18% · 32 threads"},
              {"label": "MEM", "pct": 42, "text": "26.8 / 64 GiB"},
              {"label": "/", "pct": 61, "text": "570 / 931 GiB"},
              {"label": "STORE", "pct": 54, "text": "495 / 915 GiB"},
              {"label": "NET ↓", "pct": null, "v": 1250000, "text": "1.2 MB/s"},
              {"label": "NET ↑", "pct": null, "v": 84000, "text": "84 kB/s"}],
   "lists": [{"title": "Failed", "items": ["nixi.service"], "tone": "bad"}]}]}
```

Validation (unknown keys dropped, any failure → `None`):

| Field | Rule |
|---|---|
| `title` | `_str(…, 80)`, required |
| `say`, `source` | optional, `_str(…, 200)` / `_str(…, 120)` |
| `live` | optional bool: the page may refresh it (part 4) |
| `hosts` | list of 1–6 |
| `host.name` | `_str(…, 32)` matching `[A-Za-z0-9._-]+` |
| `host.state` | `"up"` (default), `"down"` or `"stale"` |
| `host.badges` | ≤ 6 of `{k: _str(16), v: _str(60), tone?}` |
| `host.meters` | ≤ 8 of `{label: _str(12), pct: number 0–100 or null, v?: finite number ≥ 0, text?: _str(40), tone?}`; `bool`, NaN and ±inf refused |
| `host.lists` | ≤ 2 of `{title: _str(24), items: ≤ 5 × _str(80), tone?}` |
| `tone` | `"ok"`, `"warn"` or `"bad"`; when absent the page derives it from `pct` (< 70 ok, 70–89 warn, ≥ 90 bad) |

`pct: null` means unavailable, shown as "—", never as 0 (intent outcome 5).
A plugin never sends a series: the page keeps the history (part 4). The output
cap stays 64 KiB (`OUT_CAP`).

`Store.put()` (`stages.py:274`) gives a `gauges` stage one `copy` token,
whose text is a plain summary ("p620 · CPU 18% · MEM 26.8 / 64 GiB · …"), and,
when `live`, one `refresh` token holding `{"pid", "query"}` (part 4).

### 3. Host readings: `system-status` grows (`app/plugins.py:554`)

`system_status()` keeps `generation` and `failed` (user units) and adds, all
read by Nixi outside the sandbox and passed on stdin as today:

| Key | Source | Note |
|---|---|---|
| `failed_system` | `systemctl --failed --plain --no-legend` (2 s) | `null` if the query fails |
| `cpu_pct` | `/proc/stat` | difference against the previous reading |
| `mem` | `/proc/meminfo` | `{total, available}` bytes |
| `disks` | `os.statvfs` of `/` and `/nix/store` | `{path, total, used}` bytes |
| `net` | `/proc/net/dev`, all interfaces but `lo` | `{rx_bps, tx_bps}`, difference against the previous reading |
| `uptime_s` | `/proc/uptime` | |
| `host` | `socket.gethostname()` | |

- **Rates need two readings.** The module keeps the last `/proc/stat` and
  `/proc/net/dev` counters with their time. With no reading in the last
  30 s, it reads, waits 250 ms and reads again; otherwise it uses the
  difference since the last call. Each value is `null` when it couldn't be
  read.
- **Same capability, same consent.** These are all "your system status", which
  the consent card already names. The card's wording doesn't change, and a
  plugin that declared `reads: ["system-status"]` gets the new keys without
  being asked again.
- Readings go to the plugin on stdin and to the page; never to a prompt or a
  log (intent constraint "Readings stay local").

### 4. Live while visible (`index.html`, `server.py`)

- **Page:** when a `gauges` stage with a `refresh` token is open, the page
  posts `/api/stage/act {token, act: "refresh"}` every **5 s**. It stops when
  the stage closes or collapses to its tab (`stgState !== 'open'`), when
  `document.hidden`, when the page isn't really showing it (`stagePost`'s
  `shown` is false), and after **24 refreshes (2 minutes)**.
- **Server, `stage_act(…, "refresh")`:** only for the current stage's refresh
  token; refused while `Ambient.locked`. It calls `plugins.run_stage(p, query,
  fresh=True)`, a new keyword that skips the cache read but still writes it,
  and still refuses a second run of the same plugin (`Busy`, so a slow refresh
  is skipped, not queued). The new stage replaces the current one in the
  store in place (same tokens: `Store.replace(page)`), and the page gets a
  `stage_update` bus event, not `stage`, so there's no new entrance.
- **History** lives in the page: per host and meter label, the last 24 values
  (`pct`, or `v` when `pct` is null), drawn as a sparkline. It starts with the
  first reading and is dropped when the stage closes.
- **Staying up:** `stageTick` (`index.html:2362`) treats `gauges` as
  interactive (not read-only), and while it is refreshing it collapses after
  **2 minutes** without use instead of 30 s. Once refreshing stops it
  collapses as other stages do.
- **Budget:** a refresh must take under 300 ms wall time on p620 and under
  600 ms on razer (measured in verification); `nix-status` sets
  `cache_seconds: 4`.

### 5. The `term` set: the board's look (`index.html`)

- **A new stage set `term`,** chosen for kind `gauges` beside board / map /
  cinema / sky / desk / notebook (`index.html:2221-2223`).
- **Colours from the omarchy theme the page already has** (`THEME`, the
  terminal colours from kitty: background, foreground, green, yellow, red,
  blue). Background is the theme's terminal background at 96% opacity, never
  the cream paper. Text in a monospace font (`ui-monospace`, then the
  theme's terminal font if the page knows it).
- **btop-like layout:** one panel per host, with a 1 px border in the theme's
  dim foreground and the title set into the top border ("┤ p620 ├"). Inside:
  badges on one line; each meter as a row `LABEL ▕████▌     ▏ 18% · text`
  (a CSS bar, not characters) followed by a braille sparkline of its history
  (8 levels, `⠀`–`⣿`, built from the numbers by the page); lists below (failed
  units in the theme's red).
- **Accessible:** each meter row carries its value as text ("18%", "—" when
  unavailable), so colour never carries meaning alone; the sparkline is
  `aria-hidden` and the row's `aria-label` reads "CPU 18 percent". Esc closes
  as for every stage. Contrast checked as in #155 (≥ 4.5:1 for text against
  the panel).
- **Size:** within the frame's existing budget (about 340 px wide beside him,
  `stagePlace`, `index.html:2214`); rows scroll inside the panel past eight
  meters.
- **Entrance, "power on":** the card opens from a 2 px horizontal line to full
  height (`scaleY`, 180 ms), then the rows appear top to bottom 30 ms apart,
  and each bar fills from 0 to its value (200 ms). Updates move bars and
  numbers without re-running the entrance. Under reduced motion
  (`REDUCED.matches`): no scale, no stagger, no bar fill; values just change.

### 6. Accessible text and Copy

`stageText()` (`index.html:2336`) gets a `gauges` branch (title, then one line
per meter) for screen readers and the Copy button. Copy uses the server's
`copy` token (part 2), never page text.

### 7. `nix-status` becomes a `gauges` plugin (`plugins/examples/nix-status/`)

- `run` builds one host from `system_status` (part 3): CPU, MEM, `/`, STORE,
  NET ↓, NET ↑ meters; `gen` and `up` badges; a "Failed" list with user and
  system units (tone `bad`, or a single "none" with tone `ok`). It still uses
  `os.statvfs` for the store when `disks` is missing (older Nixi).
- `say`: "All fine." / "One failed service: X." / "N failed services." plus
  "Memory is high." when MEM ≥ 90%.
- `plugin.json`: `cache_seconds: 4`; phrases unchanged; `reads` unchanged.
- **Hash:** the folder changes, so a user who allowed a copied `nix-status`
  sees "Changed — check it again" once; a Nix-installed one shows "Updated".
  That is the #149 design. The README says so.

## Alternatives rejected

- **A `sysboard` kind made only for system status** (Codex): fewer choices,
  but #168 and other number plugins (UPS, GPU, build queue) would each need
  their own kind and renderer. The user chose the general look.
- **The plugin streams, or stays running:** a long-lived process in the
  sandbox, a new stream protocol, and a process to clean up. Re-running per
  refresh reuses everything #149 already checks (hash, caps, timeout).
- **The plugin reads `/proc` itself:** inside bwrap, `/proc/stat` and
  `/proc/meminfo` do show the host, but network counters are the sandbox's
  own (no shared net namespace), systemd isn't reachable, and it would be
  host access no consent named. Readings are given on stdin.
- **The plugin sends sparkline series:** a fresh sandbox has no memory of
  earlier runs, so the series would have to come from Nixi anyway. The page
  keeps it.
- **Server-side sampling on a timer while the board is open:** the same
  numbers, but sampling would no longer stop just because the page stopped
  asking. The page drives it.
- **Refresh every 4 s (agy) or 10 s (Codex):** 5 s, the user's choice.
- **Box-drawing characters for the panels:** they break on proportional
  fallback fonts and at odd widths. CSS borders with the title notched in look
  the same and reflow.

## Risks

- **A sandbox start every 5 s while open.** Each run hashes and copies the
  plugin folder and starts bwrap. Bounded by the 2-minute cap, the `Busy`
  skip, and the budget in part 4; measured on p620 and razer.
- **CPU % right after opening** is a 250 ms sample, so the first value can be
  jumpy; later ones are 5 s averages.
- **Theme colours with poor contrast** (a light theme's "terminal background"
  is light). The set uses the theme's terminal colours as a pair, and falls
  back to a fixed dark palette when contrast is under 4.5:1.
- **`systemctl --failed` (system) adds a call** per refresh (2 s timeout, run
  outside the sandbox). A hung systemd shows "—" for the list, not a hang.
- **Older Nixi + new plugin:** a `gauges` result on a Nixi before this change
  is refused ("can't show"); the README says which version is needed.

## Verification

- **Unit (fork, `python3 -m unittest discover -s tests`):**
  - `validate()` for `gauges`: a full example passes; each rule in part 2's
    table refuses its bad case (7 hosts, 9 meters, `pct` 101, NaN, `True`,
    a bad host name, a 61-character badge); unknown keys are dropped; `say`
    over 200 characters refused.
  - `run_stage` accepts `gauges` and `headlines`, refuses `commands`.
  - `plugin_stage` speaks `say` when present, "Here you go." otherwise, and
    the page event carries no `say`.
  - `system_status()` with fake `/proc` files: rates from two readings,
    `null` for an unreadable file, never 0.
  - `stage_act(refresh)`: only the current stage's token; refused while
    locked; `Busy` skips; the store's tokens are unchanged after a refresh.
  - `nix-status` in the real sandbox (the existing sandbox test class):
    returns valid `gauges`, with a `say`.
- **Page (headless Chromium, `--disable-gpu`):** a `gauges` stage renders
  in the `term` set; with fake refresh responses, bars and numbers change
  without the entrance re-running; refreshes stop on close, on collapse and
  after 24; reduced motion shows no animation.
- **Budget:** time 24 refreshes on p620 and on razer; the median is under
  300 ms and 600 ms.
- **Live on p620:** "system status" shows the dark board with this host's
  readings; it updates for 2 minutes and collapses; closing it stops the
  refresh requests (server log); he says the spoken line; a failed unit shows
  in red with its name; the screen lock stops refreshes.
